# 第 03 章 · 数据链路层原理

> **一句话定位**：解决「怎样把比特流切成一个个有边界的帧、怎样发现传输错误、怎样保证可靠交付」这三个链路层的根本问题。
> **前置知识**：第 02 章 ｜ **难度**：★★★ ｜ **建议投入**：120 分钟

## 一、学习目标

1. 能说出链路层的三大功能（封装成帧、差错控制、流量控制）与各自要解决的问题。
2. 能用字符计数法、字节填充、位填充、违规编码四种方法完成帧定界，并说明各自代价。
3. 会计算奇偶校验、二维奇偶校验、CRC 的检错能力边界。
4. 能手工完成模 2 除法，求 CRC 余数，并验证「接收方用同一多项式除余数为 0」。
5. 能推导海明码的 `2^r ≥ m + r + 1`，并把 4 位数据编码为 7 位码、定位并纠正 1 位错误。
6. 能对比停等、后退 N 帧（GBN）、选择重传（SR）三种 ARQ 的机制差异与窗口约束。
7. 能写出 PPP 与 HDLC 的帧格式，指出各字段长度。

## 二、核心概念总览

链路层夹在物理层与网络层之间，向上提供「一条看起来没有差错的链路」，向下使用物理层提供的比特流。

```
   网络层：包 Packet
        |  交下一层
        v
  +---------------------------------------------------------+
  |              数据链路层（Data Link Layer）                |
  |  功能 1 封装成帧：加帧头/帧尾，划出帧边界                 |
  |  功能 2 差错控制：检错（CRC）、纠错（海明码）、重传（ARQ） |
  |  功能 3 流量控制：滑动窗口，别把接收方淹没                |
  +---------------------------------------------------------+
        |  交下一层
        v
   物理层：比特流  ...10110010...
```

| 功能 | 解决什么问题 | 关键机制 | 本章对应 |
|------|-------------|---------|---------|
| 封装成帧 | 比特流没有边界，接收方不知道帧从哪开始 | 字符计数、字节填充、位填充、违规编码 | 3.2 / 3.7 |
| 差错控制 | 信号受噪声干扰会翻转比特 | 奇偶、二维奇偶、海明码、CRC | 3.3 / 3.4 / 3.5 |
| 可靠传输 | 检出错后要重传，且不能把接收方淹没 | 停等、GBN、SR、滑动窗口 | 3.6 |
| 流量控制 | 发送方速度可能超过接收方处理能力 | 滑动窗口、接收窗口通告 | 3.6 |

把这四块串起来就是链路层的工作流：先划帧，再验错，错了就重传，重传时用窗口控制节奏。本章后续每一节都对应这条链上的一环。

## 三、机制详解

### 3.1 链路层三大功能与两种子层视角

**为什么要单独设一层**：物理层只保证比特能传，但传过来的比特可能被噪声翻转、可能丢失、可能连边界都没有。链路层负责把这些「脏活」处理掉，让上层看到干净的帧。

链路层在工程上还可细分为两个子层（IEEE 定义）：

1. **LLC（Logical Link Control，逻辑链路控制）**：向上提供统一的接口，处理复用与流量控制，对应 IEEE 802.2。
2. **MAC（Media Access Control，介质访问控制）**：解决「多个站点共享介质时谁先发」，对应 802.3/802.11。第 04 章将展开 MAC。

### 3.2 帧定界：四种方法

比特流 `...10110010...` 连成一片，接收方必须先找到帧的起止。

1. **字符计数法**：帧首字节写入「本帧总字节数」。接收方读第一个字节就知道后面还有多少字节。缺点是**首字节一旦出错，后续所有帧全部错位**。
2. **字节填充（字符填充）**：用特殊字节 `0x7E`（01111110）做帧定界符。若载荷中本身出现 `0x7E`，就转义成 `0x7D 0x5E`；若出现转义符 `0x7D`，则转义成 `0x7D 0x5D`。转义规则是与 `0x20` 异或（`0x7E ^ 0x20 = 0x5E`，`0x7D ^ 0x20 = 0x5D`）。
3. **位填充（零比特填充）**：发送方每遇到 **5 个连续 1 就插入 1 个 0**，从而保证数据中永不出现 6 个连续 1，也就不会与定界符 `01111110` 冲突。接收方做对称的删除。
4. **违规编码**：在物理层编码中用不会在数据里出现的电平组合做定界。例如曼彻斯特编码里数据每比特都有中间跳变，可用「无跳变」表示帧边界。缺点是依赖具体编码方案。

| 方法 | 额外开销 | 抗错能力 | 典型协议 |
|------|---------|---------|---------|
| 字符计数法 | 1 字节/帧 | 差（计数错则全乱） | 早期协议 |
| 字节填充 | 平均视载荷而定 | 好 | PPP（异步链路） |
| 位填充 | 每 5 个 1 加 1 位 | 好 | HDLC、PPP（同步链路） |
| 违规编码 | 0（借用编码冗余） | 好 | 曼彻斯特类编码 |

### 3.3 奇偶校验与二维奇偶校验

**一维奇偶校验**：加 1 个校验位，使整组 1 的个数为偶数（偶校验）或奇数（奇校验）。

- 检错能力：能检出**所有奇数个比特错**，检不出任何偶数个错。
- 纠错能力：无法定位错误位置，只能检不能纠。

**二维奇偶校验**：把数据排成 m 行 n 列，每行每列各加一个校验位，共 `m + n + 1` 个校验位。

- 检错能力：能检出所有 1 位、2 位、3 位错，绝大多数 4 位错也能检出。
- 纠错能力：**当只有 1 位出错时，可由出错的行与列交叉定位，直接纠正**。

一个具体例子：4×4 数据阵列，某位出错后，其所在行与列的奇偶校验同时失败，交叉点即错误位置。

### 3.4 CRC：循环冗余校验与模 2 除法

CRC（Cyclic Redundancy Check，循环冗余校验）是链路层最主流的检错手段。

**核心思想**：把数据比特串当成一个多项式，发送方与接收方约定同一个生成多项式 `G(x)`（度数为 r），发送方在数据后补 r 个 0 做模 2 除法，把余数附在数据后发出。

**模 2 除法规则**：加法/减法都等价于**异或**（无进位、无借位），被除数最高位为 1 就与 `G(x)` 对齐异或一次，否则左移。

**计算示例**（生成多项式 `G(x) = x⁴ + x + 1`，即比特串 `10011`，r = 4；数据 `1101011011`）：

1. 数据后补 4 个 0：被除数 = `11010110110000`
2. 用 `10011` 做模 2 除法，逐步异或后得余数 `1110`
3. 发送码字 = `1101011011` + `1110` = `11010110111110`
4. 接收方用同一 `G(x)` 除该码字，余数为 `0000` → 判定无错
5. 若传输中翻转 1 位，余数变为非 0 → 判定出错并丢弃

完整的逐步异或过程见脚本 `crc_calc.py`。

**检错能力**（只要 `G(x)` 选择得当）：

1. 检出**所有单比特错**（要求 `G(x)` 含两项以上）。
2. 检出**所有双比特错**（要求 `G(x)` 不整除 `x^k + 1`，k 小于最大帧长）。
3. 检出**所有奇数个错**（要求 `G(x)` 含因子 `x + 1`）。
4. 检出**所有长度 ≤ r 的突发错误**；长度 > r 的突发错误漏检概率为 `(1/2)^r`。

**以太网 FCS 用 CRC-32**：多项式为 `0x04C11DB7`（反射形式 `0xEDB88320`），初始值 `0xFFFFFFFF`，结果再与 `0xFFFFFFFF` 异或，最后按小端序放 4 字节在帧尾，即 FCS（Frame Check Sequence，帧校验序列）。对于 1518 字节的长帧，漏检概率量级约为 `2⁻³²`。

### 3.5 海明码：能纠错的编码

CRC 只能检错，纠错要靠重传；海明码则能在接收端**直接定位并纠正 1 位错误**。

**校验位数约束**：要纠正 1 位错，需满足

```
2^r >= m + r + 1
```

其中 m 为数据位数，r 为校验位数，+1 是因为还要表示「无错」这一状态。

**位置分配**：校验位放在 2 的幂次位置（1、2、4、8……），数据位填其余位置。

以 (7,4) 码为例（m = 4，r = 3，n = 7）：

1. 校验约束验证：`2³ = 8 ≥ 4 + 3 + 1 = 8`，刚好满足。
2. 位置安排：位置 1/2/4 放校验位 P1/P2/P4，位置 3/5/6/7 放数据位 D1/D2/D3/D4。
3. 覆盖关系（按位置编号的二进制展开）：
   - P1 校验位置 1、3、5、7（编号二进制最低位为 1）
   - P2 校验位置 2、3、6、7（编号二进制次低位为 1）
   - P4 校验位置 4、5、6、7（编号二进制第三位为 1）
4. 用偶校验确定每个 P 的取值。
5. 接收方重新计算校验组奇偶性，得到校验子 S = (S4 S2 S1)，其二进制值就是出错位置；S = 0 表示无错。

**纠错能力**：最小码距 `d_min = 3`，能纠 1 位错或检 2 位错（`d_min = 2t + 1`，t = 1）。若同时出现 2 位错，海明码会「纠正」到错误位置，因此工程上通常用 CRC 检错、用重传纠错。完整编码与纠错过程见脚本 `hamming_code.py`。

### 3.6 可靠传输：停等、GBN、SR

检出错之后要重传，这就是 ARQ（Automatic Repeat reQuest，自动重传请求）。

**基本要素**：序号（区分新旧帧）、确认 ACK、超时计时器、重传。

| 协议 | 发送窗口 | 接收窗口 | 重传范围 | 确认方式 |
|------|---------|---------|---------|---------|
| 停等 Stop-and-Wait | 1 | 1 | 仅当前帧 | 逐帧确认 |
| 后退 N 帧 GBN | W > 1 | 1 | 从丢失帧起整窗重传 | 累积确认 |
| 选择重传 SR | W > 1 | W > 1 | 只重传丢失帧 | 逐帧确认 |

**窗口尺寸约束**（序号位宽为 n 时）：

1. **GBN：`W ≤ 2ⁿ − 1`**。因为接收窗口为 1，若 W 取满 `2ⁿ`，新老序号会重叠导致接收方无法区分。
2. **SR：`W ≤ 2ⁿ⁻¹`**。发送窗口与接收窗口各占一半序号空间，才能保证不混淆。

**利用率计算**：设 `a = 传播时延 / 发送时延`，停等协议的利用率为

```
U = 1 / (1 + 2a)
```

代入示例：帧发送时延 1 ms，单程传播时延 4 ms，则 `a = 4`，`U = 1/(1+8) = 11.1%`。若用窗口 `W ≥ 1 + 2a = 9` 的流水线协议，利用率可接近 100%。

三种协议在丢包率 0.1、窗口 4 下的总发送帧数、重传次数与信道利用率对比见脚本 `arq_simulator.py`。

### 3.7 PPP 与 HDLC 帧格式

**PPP（Point-to-Point Protocol，点对点协议）**：用于拨号、专线的点对点链路，帧格式如下（异步链路用字节填充，同步链路用位填充）。

| 字段 | 长度 | 取值 | 作用 |
|------|------|------|------|
| Flag | 1 B | `0x7E` | 帧定界（首尾各一个） |
| Address | 1 B | `0xFF` | 固定值，PPP 只用于点对点故无实际地址 |
| Control | 1 B | `0x03` | 固定值，无编号帧 |
| Protocol | 2 B | 如 `0x0021`=IPv4、`0xC021`=LCP | 标识载荷类型 |
| Information | 0~1500 B | — | 载荷，默认最大长度 1500 B |
| FCS | 2 或 4 B | CRC-16/CRC-32 | 差错检测 |
| Flag | 1 B | `0x7E` | 帧结束定界 |

**HDLC（High-level Data Link Control，高级数据链路控制）**：面向比特，用位填充。

| 字段 | 长度 | 取值 | 作用 |
|------|------|------|------|
| Flag | 1 B | `0x7E` | 帧定界 |
| Address | 1 B | — | 从站/目的地址 |
| Control | 1 B | — | 帧类型与序号（I/S/U 帧） |
| Information | 变长 | — | 载荷 |
| FCS | 2 或 4 B | CRC-16/CRC-32 | 差错检测 |
| Flag | 1 B | `0x7E` | 帧结束定界 |

两者最本质的区别：PPP 面向字节（可做字节填充），HDLC 面向比特（做位填充），这也是各自适用的链路类型的必然结果。

## 四、动手验证

### 4.1 `crc_calc.py` —— 模 2 除法与以太网 FCS

**演示什么**：用 `G = 10011`（x⁴+x+1）逐步打印模 2 除法的异或过程，再算 CRC-32 并与 `zlib.crc32` 对照。

**运行命令**：`python3 crc_calc.py` 或 `python3 crc_calc.py 1101011011`。

**关键输出片段**：

```
1     0       11010110110000            01001110110000
2     1       01001110110000            00000010110000
3     6       00000010110000            00000000101000
4     8       00000000101000            00000000001110
>>> 余数（CRC）= 1110
>>> 余数为 0，校验通过
手算结果   : 0xFE2F1037
zlib 对照  : 0xFE2F1037
```

**从输出看出的结论**：经典教材例题 `1101011011` 在 `10011` 下的余数正是 `1110`；接收方对码字再除一次余数为 0；注入 1 位错误后余数变成非 0，证明 CRC 的有效性。CRC-32 手算结果与 zlib 库完全一致。

### 4.2 `hamming_code.py` —— (7,4) 海明码编码与纠错

**演示什么**：4 位数据编码为 7 位，注入 1 位错误后用校验子定位并纠正。

**运行命令**：`python3 hamming_code.py` 或 `python3 hamming_code.py 1011 5`。

**关键输出片段**：

```
>>> 编码结果（位置1..7）= 0110011
翻转位置 5：0110011  ->  0110111
>>> 校验子 S = 5（二进制 101）
    校验子 = 5 不为 0，错误位置就是第 5 位。
    提取数据位 3/5/6/7 = 1011（原始数据 1011，恢复正确）
```

**从输出看出的结论**：校验子的二进制值直接等于出错位置；`2³ = 8 ≥ 4 + 3 + 1` 刚好满足约束，说明 (7,4) 是 r 的最小取值。把错误位置改成其他值可验证定位总是成立。

### 4.3 `arq_simulator.py` —— 三种 ARQ 性能对比

**演示什么**：在丢包率 0.1、窗口 4 下传输 100 帧，统计总发送帧数、重传次数与信道利用率。

**运行命令**：`python3 arq_simulator.py` 或 `python3 arq_simulator.py 0.2 8`。

**关键输出片段**：

```
协议                总发送帧数    重传次数    轮次数    信道利用率
停等                       114          14       114        17.54%
后退 N 帧 GBN              131          31        33        38.02%
选择重传 SR                109           9        31        42.92%
```

**从输出看出的结论**：停等因每帧等待一个 RTT，利用率只有 17.5%；GBN 能流水发送但丢一帧牵连整窗重传；SR 只补丢失帧，利用率最高。窗口 W 增大时 GBN 的重传量随之膨胀（W=16 时降至 33.1%），而 SR 稳步提升至 61.7%。

### 4.4 `framing_demo.py` —— 字节填充与位填充

**演示什么**：对含 `0x7E`/`0x7D` 的载荷做字节填充，对含长串 1 的比特流做位填充，并对称去填充。

**运行命令**：`python3 framing_demo.py`。

**关键输出片段**：

```
原始载荷（5 字节）: 7E 41 7D 42 7E
>>> 填充后整帧（10 字节）: 7E 7D 5E 41 7D 5D 42 7D 5E 7E
原始 : 01111110 11111100
填充 : 01111101 01111101 00
>>> 原始 16 bit -> 填充后 18 bit，多了 2 个填充位。
填充后比特串中最长的连续 1 的个数 = 5
```

**从输出看出的结论**：字节填充把 5 字节载荷膨胀为 7 字节；位填充保证填充后最长连续 1 不超过 5，永不出现定界符 `01111110`。两种去填充都能精确还原。

下表汇总本章涉及的两类「报文」：PPP 帧格式，以及 CRC 计算所用的生成多项式参数。

| 字段 | 长度 | 作用 | 常见取值 |
|------|------|------|---------|
| PPP Flag | 1 B | 帧首尾定界 | `0x7E` |
| PPP Address | 1 B | 固定广播地址（点对点无意义） | `0xFF` |
| PPP Control | 1 B | 固定无编号帧 | `0x03` |
| PPP Protocol | 2 B | 载荷协议号 | `0x0021` IPv4、`0xC021` LCP |
| PPP Information | ≤1500 B | 载荷 | 默认 MRU 1500 B |
| PPP FCS | 2 或 4 B | CRC-16 或 CRC-32 | 2 字节时 CRC-16 |
| HDLC Flag | 1 B | 帧定界 | `0x7E` |
| HDLC Address | 1 B | 从站地址 | 命令/响应区分 |
| HDLC Control | 1 B | 帧类型与序号 | I/S/U 帧 |
| CRC 生成多项式 | r+1 位 | 决定检错能力 | `10011`（x⁴+x+1） |
| CRC 余数 | r 位 | 附在数据后一起发送 | 本算例 `1110` |
| 以太网 FCS | 4 B | CRC-32，小端序 | `37 10 2F FE` |
| 海明码校验位 | r 位 | 放 2 的幂次位置 | (7,4) 码 r=3 |
| 海明码数据位 | m 位 | 放其余位置 | (7,4) 码 m=4 |
| 海明码校验子 | r 位 | 二进制值=出错位置 | 0 表示无错 |

## 六、易混概念对比

| 概念 A | 概念 B | 核心区别 | 典型场景 |
|--------|--------|---------|---------|
| 检错 | 纠错 | 前者只发现错误，后者能定位并改正 | CRC vs 海明码 |
| 字节填充 | 位填充 | 前者以字节为单位转义，后者以比特为单位插 0 | PPP 异步 vs HDLC |
| 字符计数法 | 字节填充 | 前者靠长度字段，后者靠定界符与转义 | 计数法一错全乱 |
| GBN | SR | 前者丢包后重传整窗，后者只重传丢失帧 | 接收窗口 1 vs W |
| 累积确认 | 逐帧确认 | 前者确认号表示「到此为止都收到」 | GBN vs SR |
| CRC-16 | CRC-32 | 余数位数不同，检错强度不同 | PPP 可选 vs 以太网 FCS |
| 停等 | 滑动窗口 | 前者窗口为 1，利用率低 | 简单链路 vs 高速链路 |

## 七、工程实践与最佳实践

1. **链路层检错交给 CRC，纠错交给重传**——CRC 结构简单、速度快，检测能力足够；纠错编码（如海明码）在数据链路层很少单独用，因为一旦误纠反而更难发现。
2. **生成多项式必须选标准值**——以太网固定 CRC-32（`0x04C11DB7`），PPP 可选 CRC-16/CRC-32，两端必须一致，否则全部帧被丢弃。
3. **FCS 按小端序放帧尾**——以太网 FCS 的 4 个字节按低字节在前写入，抓包工具会自动解析，但手写解析器最容易在这里出错。
4. **帧定界优先选位填充或字节填充**——不要用字符计数法，因为首字节出错会导致后续帧全部错位，且无法自动恢复。
5. **滑动窗口大小受序号位宽约束**——GBN 必须 `W ≤ 2ⁿ − 1`，SR 必须 `W ≤ 2ⁿ⁻¹`；越界会导致序号歧义、接收方无法区分新旧帧。
6. **高带宽长时延链路必须用大窗口**——由 `U = 1/(1+2a)`，a 越大停等利用率越低。卫星链路 a 可达上百，必须用选择性重传。
7. **SR 的代价是接收端缓存**——接收端要缓存乱序帧直到缺口补齐，内存与逻辑复杂度上升，低端设备常用 GBN 折中。
8. **ARQ 超时时间要大于 RTT**——超时过短会造成不必要的重传，反而降低有效吞吐；超时过长则恢复慢。
9. **PPP 的 MRU 默认 1500**——与以太网 MTU 对齐，跨 PPP 链路时要注意两端 MRU/MTU 一致，否则大包被丢弃。
10. **链路层校验通过不代表数据正确**——CRC 存在漏检概率（CRC-32 约 2⁻³²），上层还需要 TCP 校验和等机制兜底。
11. **注意「帧长」与「有效载荷」的区别**——以太网最小帧 64 B、最大 1518 B，扣除 14 B 头 + 4 B FCS 后载荷最多 1500 B，这就是 MTU 的由来（第 04 章展开）。

## 八、常见陷阱清单

| # | 现象 | 根因 | 排查 / 规避 |
|---|------|------|-------------|
| 1 | 接收端把载荷中的 0x7E 当成帧尾 | 发送方未做字节填充 | 检查链路层是否启用转义 |
| 2 | 填充后仍出现 01111110 | 位填充计数逻辑写错（应为满 5 插 0） | 核对填充/去填充是否严格对称 |
| 3 | 转义序列被二次转义 | 去填充时把 0x7D 0x5E 当作普通数据 | 先判断转义符再取下一个字节 |
| 4 | CRC 校验全失败 | 两端生成多项式不一致 | 统一为标准多项式并核对大小端 |
| 5 | 手算 CRC 余数总差一位 | 忘了在数据后补 r 个 0 | 被除数 = 数据 + r 个 0 |
| 6 | 海明码纠错后数据仍错 | 发生了 2 位错，被「纠正」到错误位置 | 用 CRC 先检错，或改用扩展海明码 |
| 7 | 窗口开到 2ⁿ 导致序号歧义 | GBN 违反 W ≤ 2ⁿ−1 | 按序号位宽计算窗口上限 |
| 8 | SR 接收端缓存溢出 | 窗口过大且长期收不齐 | 限制窗口并设置超时清缓存 |
| 9 | 停等在长时延链路上吞吐极低 | a 很大，利用率 = 1/(1+2a) | 改用滑动窗口协议 |
| 10 | 超时重传过于频繁 | 超时时间小于 RTT | 超时设为略大于 RTT |
| 11 | 以为 CRC 能纠错 | 混淆 CRC 与纠错码 | CRC 只检错，纠错靠 ARQ |
| 12 | PPP 两端 MRU 不一致导致大包丢失 | 一端默认 1500、一端被调小 | 两端统一 MRU/MTU |

## 九、自测练习

1. 说明链路层三大功能，并各举一个具体机制。
2. 对比字符计数法、字节填充、位填充三种帧定界方法的优缺点。
3. 计算题：生成多项式 `G(x) = x⁴ + x + 1`（`10011`），数据 `1011001`，求 CRC 余数与发送码字。
4. 计算题：数据 8 位，求海明码最少需要几位校验位；若数据 16 位呢？
5. 计算题：某链路帧发送时延 2 ms，单程传播时延 10 ms，求停等协议利用率；若改用窗口至少多大才能跑满？
6. 计算题：序号位宽 n = 3，分别求 GBN 与 SR 的最大窗口。
7. 计算题：以太网 FCS 用 CRC-32，随机错误被漏检的概率数量级是多少？
8. 排障题：某 PPP 链路大量帧被丢弃，一端日志显示 FCS 错误，列出至少三条排查方向。
9. 排障题：某滑动窗口协议在高速链路上吞吐只有标称的 20%，分析原因与改进方向。
10. 说明为什么字节填充要把 0x7D 也转义，只转义 0x7E 会出什么问题。
11. 说明 GBN 与 SR 在「接收窗口」上的本质差异，以及各自对序号空间的要求。
12. 给出二维偶校验能纠 1 位错的理由。

<details>
<summary>参考答案</summary>

1. 封装成帧 = 位填充/字节填充划出帧边界；差错控制 = CRC 检错 + ARQ 重传；流量控制 = 滑动窗口控制发送速率。

2. 字符计数法实现最简单但首字节出错会使后续帧全部错位；字节填充面向字节、易实现，但依赖 8 位字符集且载荷可能膨胀；位填充与字符集无关、健壮性好，但需要收发两端严格对称的实现。

3. 被除数 = `1011001` + `0000` = `10110010000`。用 `10011` 做模 2 除法：最高位对齐异或逐步进行，得余数 `1010`。发送码字 = `1011001` + `1010` = `10110011010`。

4. 8 位数据：需满足 `2^r ≥ 8 + r + 1 = 9 + r`。试 r=4：`2⁴ = 16 ≥ 13`，成立，故 r=4（(12,8) 码）。16 位数据：`2^r ≥ 17 + r`，试 r=5：`32 ≥ 22` 成立，故 r=5（(21,16) 码）。

5. `a = 10/2 = 5`；`U = 1/(1 + 2×5) = 1/11 ≈ 9.1%`。要跑满需 `W ≥ 1 + 2a = 11`。

6. n=3：GBN 最大窗口 `2³ − 1 = 7`；SR 最大窗口 `2^(3−1) = 4`。

7. 漏检概率约为 `(1/2)^32 ≈ 2.3×10⁻¹⁰`，即约 10⁻¹⁰ 量级。

8. 方向：① 两端 CRC 多项式或大小端约定不一致；② 链路质量差导致误码率高（检查物理层误码、光功率、线缆）；③ MRU/MTU 不匹配导致大帧被截断；④ 位填充/字节填充实现不对称导致帧边界错乱。

9. 可能原因：① 窗口太小，`W < 1 + 2a`，链路大量空转；② 超时设置不当导致无效重传；③ 丢包率高使 GBN 反复重传整窗；④ 序号位宽不足限制了窗口。改进方向：增大窗口、改用 SR、合理设置超时。

10. 因为转义后的序列里含有 0x7D，如果只转义 0x7E 而不转义 0x7D，那么接收方看到 0x7D 时无法判断它是数据还是转义前缀；当载荷本身含 0x7D 时，后面的字节会被错误地当作被转义字节，导致还原错误。因此 0x7D 必须转义为 0x7D 0x5D。

11. GBN 的接收窗口恒为 1，接收方只按序接收，乱序帧一律丢弃，因此序号空间只需容纳发送窗口：`W ≤ 2ⁿ − 1`；SR 的接收窗口为 W，接收方要缓存乱序帧，发送窗口与接收窗口各占一半序号空间，故 `W ≤ 2ⁿ⁻¹`。

12. 二维偶校验中，1 位错误会同时破坏其所在行的行校验和所在列的列校验，行与列各有一个校验失败，二者的交叉点就是出错位置，故可直接定位并翻转纠正。

</details>
