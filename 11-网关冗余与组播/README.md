# 第 11 章 · 网关冗余与组播

> **一句话定位**：解决两个「一对多」问题 —— 多台设备如何共同充当一个网关（VRRP/HSRP/GLBP），以及一份流量如何只发给需要它的一群人（组播 + PIM）。读完能手算虚拟 MAC、判断主备切换时间、讲清 (*,G) 与 (S,G) 的差别和 RPF 防环。
> **前置知识**：第 06 章（IPv4 与子网）、第 09 章（OSPF） ｜ **难度**：★★★ ｜ **建议投入**：150 分钟

## 一、学习目标

1. 能写出 VRRP 虚拟 MAC 的生成规则，并说明为什么主备切换对主机完全透明。
2. 能算出 VRRP 的 Skew_Time 与 Master_Down_Interval，并解释为什么优先级低的设备等待更久。
3. 能列出 VRRP、HSRP、GLBP 三者在角色命名、虚拟 MAC、组播地址、是否支持负载分担上的差异。
4. 能默写常见 ICMP 类型码（0/3/5/8/11/12）与 Type 3 下的关键 code（0/1/3/4）。
5. 能手算任意 IPv4 组播地址对应的 MAC、解释「32:1 重叠」的成因与主机侧过滤方式，并对比 IGMP v1/v2/v3 在离开机制、源过滤上的能力差异，说明 IGMP Snooping 解决了什么问题。
6. 能画出 PIM-SM 从 (*,G) 共享树切换到 (S,G) 最短路径树的全过程，并说明 RPF 检查为什么是组播唯一的防环手段。

## 二、核心概念总览

```
                        「一对多」的两类问题
        ┌──────────────────────────┬──────────────────────────────┐
        │ 多台设备充当一个网关      │ 一份流量发给一群人            │
        │ （冗余 + 单点故障消除）   │ （组播，节省带宽）            │
        ├──────────────────────────┼──────────────────────────────┤
        │ VRRP（标准）              │ 组播地址：224.0.0.0/4        │
        │ HSRP（Cisco）             │ 组播 MAC：01:00:5E + 低 23 位 │
        │ GLBP（Cisco，带负载分担） │ IGMP（主机↔路由器）           │
        │ 虚拟 IP + 虚拟 MAC        │ PIM（路由器↔路由器）          │
        │ 优先级 + 抢占             │ RPF 检查 + (*,G)/(S,G) 表项   │
        └──────────────────────────┴──────────────────────────────┘
```

两块内容的共同点是「用一个虚拟身份隐藏真实的多个实体」：网关冗余用**虚拟 IP + 虚拟 MAC** 把多台物理设备伪装成一台，主机只需记住一个网关地址；组播用**组地址**把「一份流量」分发给一组主机，发送者不需要知道接收者是谁。两者的实现差异在于：VRRP 解决的是**可用性**，PIM 解决的是**效率与防环**。

## 三、机制详解

### 3.1 VRRP：虚拟 MAC 与选举规则

VRRP 让多台路由器共享一个**虚拟 IP（VIP）** 和一台**虚拟路由器**。核心只有一条：MAC 与 IP 都是虚拟的，所以主机切换网关设备时完全无感知。

**虚拟 MAC 生成规则**（RFC 5798 / VRRPv2 一致）：

`虚拟 MAC = 00-00-5E-00-01-{VRID}`

- 前 3 字节 `00-00-5E` 是 IANA 分配给 VRRP 的组织唯一标识（OUI）。
- 第 4、5 字节固定为 `00-01`，表示这是 VRRP 协议。
- 第 6 字节就是 **VRID**，范围 1~255。

例如 VRID = 1 时虚拟 MAC 为 `00:00:5E:00:01:01`，与哪台设备当 Master 无关。主机执行 `arp -a` 看到的网关 MAC 就是它，主备切换时这个值不变 —— **这是 VRRP 对主机透明的根本原因**。

**选举规则**（按顺序）：

1. 接口 IP 就是 VIP 的路由器（Address Owner，优先级固定 255）永远是 Master。
2. 否则比较接口优先级（1~254，默认 100），大者当选 Master。
3. 优先级相同时，比较接口主 IP 地址，大者当选。
4. 优先级 0 表示不参与选举；Master 主动发优先级 0 的通告表示「我要退位」。

**计时器**：

- Master 每 `Advertisement_Interval`（默认 **1 秒**）向 **224.0.0.18** 发一次通告，目的 MAC `01:00:5E:00:00:12`。
- Backup 的接管时间 `Master_Down_Interval = 3 × Advertisement_Interval + Skew_Time`。
- `Skew_Time = (256 − Priority) / 256` **秒**。

代入：优先级 100（默认）时 `Skew = (256−100)/256 = 0.609` 秒，`Master_Down_Interval = 3×1 + 0.609 = 3.609` 秒；优先级 200 时 `Skew = 0.219` 秒，接管时间 `3.219` 秒。**优先级越高，Skew 越小、接管越快**，这样高优先级设备能第一时间抢回主位。

**抢占（Preempt）**：VRRP 默认开启抢占。原 Master 恢复后，只要优先级高于现任 Master 就会夺回主位。配置 `no preempt` 可关闭，避免链路抖动导致的反复切换。

**认证**：VRRPv2 支持明文口令（Simple Text）与 IP AH 认证；**RFC 5798（VRRPv3）取消了认证字段**，改用 IPsec 保护。因此「认证」只在 VRRPv2 设备上存在，跨版本混用要特别小心 —— 认证不一致的表现不是报错，而是**双 Master**。

### 3.2 HSRP 与 GLBP：思科体系的另外两种选择

| 对比项 | VRRP | HSRP | GLBP |
|---|---|---|---|
| 标准化 | RFC 5798 公开标准 | 思科私有 | 思科私有 |
| 角色命名 | Master / Backup | Active / Standby | AVG（网关）/ AVF（转发者） |
| 虚拟 MAC | `00:00:5E:00:01:{VRID}` | v1 `0000.0C07.ACxx`，v2 `0000.0C9F.Fxxx` | `0007.B400.{组}.{AVF}` |
| 组号范围 | VRID 1~255 | v1 0~255，v2 0~4095 | 组 0~1023 |
| 报文承载 | IP 协议号 112 | UDP 1985 | UDP 3222 |
| 组播地址 | 224.0.0.18 | 224.0.0.2 | 224.0.0.102 |
| 默认优先级 | 100 | 100 | 100 |
| 默认抢占 | 开启 | 关闭 | 开启 |
| 默认计时 | Advertisement 1 秒 | Hello 3 秒 / Hold 10 秒 | Hello 3 秒 / Hold 10 秒 |
| 负载分担 | 不支持（只有主备） | 不支持 | 支持（最多 4 个 AVF） |
| 备份数量 | 多个 Backup | 仅 1 个 Standby | 多个 AVF |

**GLBP 的价值**：VRRP/HSRP 只有一台设备在转发，另一台闲着；GLBP 让最多 4 台设备**同时转发**，每台主机被分配到不同的虚拟 MAC（AVF 的 MAC），从而把上行流量分摊到多台设备。三种负载分担策略：round-robin（轮询）、weighted（按权重）、host-dependent（按主机，同一主机始终走同一台）。

### 3.3 ICMP：网络层的「快递员回执」

ICMP 不承载用户数据，只传递控制与差错信息。常用类型：

| Type | 名称 | 常见 Code 与含义 |
|---|---|---|
| 0 | Echo Reply | 回显应答（`ping` 的成功响应） |
| 3 | Destination Unreachable | 0=网络不可达，1=主机不可达，2=协议不可达，3=端口不可达，4=需要分片但 DF 置位 |
| 5 | Redirect | 0=网络重定向，1=主机重定向（通知有更优下一跳） |
| 8 | Echo Request | 回显请求（`ping` 发出的） |
| 11 | Time Exceeded | 0=传输中 TTL 超时，1=分片重组超时 |
| 12 | Parameter Problem | 0=指针指向出错的字节（IP 头字段错误） |

工程上最常用的三条判据：

- `time exceeded (code 0)` 来自中间路由器 → 这是 `traceroute` 的工作原理（TTL 从 1 递增）。
- `destination unreachable (code 3, 端口不可达)` 来自目的主机 → `traceroute` 用它判断「到达了」。
- `destination unreachable (code 4, 需要分片但 DF 置位)` → **MTU 黑洞的典型信号**，中间链路 MTU 小于报文且不允许分片。

### 3.4 组播地址与 MAC 映射

IPv4 组播使用 **D 类地址 224.0.0.0/4**（224.0.0.0 ~ 239.255.255.255），IPv6 使用 **ff00::/8**。组地址分为：

- **永久组地址**：IANA 分配的、有固定含义的地址，如 224.0.0.1（本网段所有主机）、224.0.0.2（本网段所有路由器）、224.0.0.5（所有 OSPF 路由器）、224.0.0.6（OSPF 的 DR/BDR）、224.0.0.9（RIPv2 路由器）、224.0.0.13（所有 PIM 路由器）、224.0.0.18（VRRP）。
- **临时组地址**：动态分配的、只在会话期间有效的地址，如 239.0.0.0/8 私用段。

**IPv4 组播到 MAC 的映射**：`MAC = 01:00:5E + 组播 IP 的低 23 位`。

组播组号有 28 位，而 MAC 只能容纳 23 位，因此**丢掉 5 位**，导致 `2^5 = 32` 个不同的组映射到同一个 MAC，这就是 **32:1 地址重叠**。

代入：224.0.1.1 → 二进制 `11100000.00000000.00000001.00000001`，低 23 位 = `0 0000000.00000001.00000001`，MAC = `01:00:5E:00:01:01`。而 224.128.1.1 → `11100000.10000000.00000001.00000001`，低 23 位同样 = `0 0000000.00000001.00000001`，MAC 也是 `01:00:5E:00:01:01` —— **这两个不同的组会撞在同一个 MAC 上**。

完整计算：可用的组播地址共 `2^28` 个，每个 MAC 对应 `2^5 = 32` 个组，`2^28 / 2^5 = 2^23`，恰好整除，因此映射是严格的 32:1（每一个组播 MAC 恒定对应 32 个组，没有边界例外）。**主机侧必须靠 IP 层再做一次过滤**，否则会收到不属于自己组的数据。

### 3.5 IGMP 与 IGMP Snooping

IGMP 是主机与本地组播路由器之间的「加组/退组」协议，三种版本：

- **IGMPv1（RFC 1112）**：主机发 Membership Report（类型 0x12）加组；**没有离开报文**，路由器只能靠查询超时判断主机已退出。查询间隔 60 秒，最大响应时间 10 秒。
- **IGMPv2（RFC 2236）**：新增 **Leave Group（类型 0x16）** 与**特定组查询（Group-Specific Query）**，主机退组时立即上报，路由器再针对该组发查询确认是否真无接收者，显著缩短了离开延迟；同时引入**报告抑制**（同组只有一台主机应答，减少冗余报文）。
- **IGMPv3（RFC 3376）**：新增**源过滤**，报告类型 0x22，支持 INCLUDE（只接收指定源）与 EXCLUDE（接收除指定源外的所有源）两种模式。这是 **SSM（Source-Specific Multicast）**的基础。

**IGMP Snooping**：二层交换机默认把组播帧当广播泛洪。开启 Snooping 后，交换机会监听 IGMP 报文，建立「组播 MAC → 端口」转发表，只向真正有接收者的端口转发，从而把组播流量限制在必要的链路上。注意：Snooping 只看 IGMP，若网络里没有 IGMP 报文（如纯静态组播），需要配置静态组播转发表项。

### 3.6 PIM-SM：从共享树到最短路径树

组播路由的核心难点是「没有目的地址可查表」—— 数据包的目的地址是一个组，不是一个具体主机。因此组播转发方向只能由**源**决定，这就是 **RPF（Reverse Path Forwarding，反向路径转发）**：

**只有组播报文从「到源的最短路径接口」进来时，才接受并转发；否则丢弃。**

PIM-SM（稀疏模式）的建立过程：

1. **接收者加组**：接收主机发 IGMP Report，最后一跳路由器产生 (*,G) 表项的雏形。
2. **建立共享树 RPT**：最后一跳路由器对 **RP（Rendezvous Point，汇合点）** 做 RPF 检查，向 RPF 邻居发送 `Join(*, G)`，逐跳向上直到 RP。此时形成以 RP 为根的**共享树（RPT）**，表项是 `(*, G)`。
3. **源开始发送**：源侧第一跳路由器（DR）没有 (S,G) 表项，于是把组播报文封装进 **PIM Register** 单播报文发给 RP。
4. **RP 向源建立 SPT**：RP 对源做 RPF 检查，向源方向发送 `Join(S, G)`，建立 `(S, G)` 表项。此后源流量沿最短路径树到达 RP。
5. **Register-Stop**：RP 通过 SPT 收到 (S,G) 数据后，向源侧 DR 发 Register-Stop，停止单播封装。
6. **SPT 切换**：最后一跳路由器发现「直接到源比经 RP 更近」，于是向源方向发 `Join(S, G)`，建立 (S,G) 表项，等新路径流量到达后再向 RP 发 `Prune(S, G)`，退出共享树。
7. **剪枝**：RP 从 (S,G) 出接口中移除该下游；若 (*,G) 已无出接口且长期无接收者，RP 会向源方向发 Prune。

**RP 与 BSR**：RP 是 PIM-SM 的「树根」，全网必须知道 RP 是谁。静态指定 RP 最简单但无冗余；动态方式用 **BSR（Bootstrap Router）** 选举出 BSR，由 BSR 把 RP 信息（RP-Set）泛洪给全网（由 C-RP 单播向 BSR 注册候选）。常用做法是 **Anycast RP**（多个 RP 共享同一个地址，靠 MSDP 或 PIM 自身同步源信息）。

### 4.1 `vrrp_election.py` —— 选举、抢占、虚拟 MAC

```
运行: python3 vrrp_election.py
```

关键输出：

```
路由器    优先级    接口 IP           角色        Skew时间    Master_Down_Interval
R1        200       203.0.113.1       Master      0.219s      3.219s
R2        100       203.0.113.2       Backup      0.609s      3.609s
R3        150       203.0.113.3       Backup      0.414s      3.414s
>>> 选举结果：Master = R1，Backup = R3
```

脚本还演示了 R1 掉线后 R3 接管、R1 恢复时「开启抢占」与「关闭抢占」的差异，以及认证口令不一致导致的**双 Master**场景。结论：虚拟 MAC 固定为 `00:00:5E:00:01:{VRID}`，与物理设备无关；Skew 时间随优先级升高而减小，保证高优先级设备先接管。

```
运行: python3 multicast_mapping.py
```

关键输出：

```
运行: python3 multicast_tree.py
```

关键输出（阶段五）：

```
R1        (S, 239.1.1.1)        源直连接口            → R2 (RP)、→ R3 (SPT)
```

## 六、易混概念对比

| 概念 A | 概念 B | 核心区别 | 典型场景 |
|---|---|---|---|
| VRRP | HSRP | VRRP 是公开标准（Master/Backup），HSRP 是思科私有（Active/Standby） | 多厂商 vs 纯思科环境 |
| VRRP/HSRP | GLBP | 前两者只有一台转发，GLBP 最多 4 台同时转发做负载分担 | 主备冗余 vs 负载分担 |
| 虚拟 IP | 虚拟 MAC | VIP 是给主机看的网关地址，虚拟 MAC 是数据链路层的身份 | 主机 ARP 看到的是虚拟 MAC |
| 永久组地址 | 临时组地址 | 前者 IANA 固定分配（224.0.0.5），后者动态分配（239.x） | OSPF vs 视频会议 |
| IGMP | PIM | IGMP 管主机↔本地路由器，PIM 管路由器↔路由器 | 接入层 vs 骨干层 |
| (*,G) | (S,G) | `(*,G)` 是共享树（根在 RP，与源无关），`(S,G)` 是最短路径树 | RPT vs SPT |
| PIM-DM | PIM-SM | DM 先泛洪再剪枝（推模式），SM 先加组再建树（拉模式） | 小网密集 vs 大网稀疏 |
| Type 3 code 1 | Type 3 code 3 | code 1 = 主机不可达，code 3 = 端口不可达 | 路由问题 vs 服务未监听 |

## 七、工程实践与最佳实践

1. **网关冗余与生成树/路由协议一起规划**。原因：VRRP 的 Master 必须是该网段的转发最优路径，否则会出现「网关在这台、流量却要从那台绕」的非最优转发。
2. **VRRP 优先级要拉开档次（如 200 / 150 / 100）**。原因：优先级相同会退化成「比接口 IP」，结果难以预期；拉开档次可保证主备顺序符合规划。
3. **上联链路带宽不对等时关闭抢占或加抢占延迟**。原因：主设备链路抖动会导致网关反复切换，每次切换都会引发 ARP 更新与短暂丢包。
4. **VRRP/HSRP 必须与上行链路状态联动（Track）**。原因：如果只监控接口 up/down，Master 的上联断了但接口还在，网关仍会吸引流量形成黑洞。用 `track` 绑定上行接口或 BFD 会话。
5. **跨厂商环境统一用 VRRP**。原因：HSRP/GLBP 是思科私有，异厂商设备无法互通。
6. **VRRPv2 与 VRRPv3 混用前先确认认证行为**。原因：v3 取消认证字段，v2 的认证配置在 v3 上无效，容易出现双 Master。
7. **组播规模大时优先用 IGMP Snooping 抑制泛洪**。原因：不开启 Snooping 的二层交换机会把组播帧泛洪到所有端口，等于把组播退化成广播。
8. **组播域的 RP 要做冗余（Anycast RP + MSDP）**。原因：单 RP 是整网组播的单点故障，RP 一倒，所有新的 (*,G) 树都建不起来。
9. **组播排障先查 RPF**。原因：RPF 失败是「IGMP 正常、表项正常、流量不来」的头号原因，用 `show ip rpf <源>` 一眼可查。
10. **SSM 场景直接用 IGMPv3 + PIM-SSM，不必走 RP**。原因：SSM 不需要 RP，直接在源与接收者之间建 (S,G) 树，省去共享树切换的开销与复杂度。
11. **MTU 规划时预留组播封装开销**。原因：GRE/IPsec 隧道承载组播会额外占字节，MTU 不规划会出现「建树成功但大包全丢」。
12. **监控 VRRP 状态切换与组播组数量**。原因：频繁切换意味着链路或 Track 配置有问题；组数量暴涨往往意味着组播泄漏或地址规划失控。

## 八、常见陷阱清单

| # | 现象 | 根因 | 排查 / 规避 |
|---|------|------|-------------|
| 1 | 出现双 Master，网关 MAC 冲突 | VRID 重复、认证不一致、或 Virtual IP 配错 | 核对两端 VRID 与认证；`display vrrp` 看状态 |
| 2 | 主备切换后主机仍不可达 | 主机 ARP 缓存里还是旧 MAC，或交换机 MAC 表未更新 | Master 切换后应发免费 ARP；检查交换机 MAC 老化 |
| 3 | 网关切换时间远超 3 秒 | Advertisement 间隔被改大，或 Track 触发了延迟 | 核对 `advertisement-interval` 与抢占延迟配置 |
| 4 | 优先级更高的设备抢不回主位 | 配置了 `no preempt` | 确认抢占开关；必要时手动 `clear`/`reset` |
| 5 | 接口 up 但网关不转发 | 上联链路已断，VRRP 只监控本接口状态 | 配置 `track` 绑定上联接口或 BFD |
| 6 | 组播流量泛洪到所有端口 | 未开启 IGMP Snooping，或组播地址是 224.0.0.x 永久组 | 开 Snooping；永久组地址本就按泛洪处理 |
| 7 | 主机收到不属于自己的组播 | 32:1 MAC 重叠，二层无法区分 | 依赖 IP 层过滤；尽量规划不重叠的组前缀 |
| 8 | IGMP 加组了但收不到流量 | RPF 检查失败（单播路由不对称） | `show ip rpf <源>` 检查入接口是否与 RPF 接口一致 |
| 9 | 同一份流量收到两份 | RPT 与 SPT 同时转发，切换窗口内重叠 | 属正常过渡；若长期双份说明 Prune 未生效 |
| 10 | RP 挂掉后新接收者加不进来 | 无冗余 RP，或 BSR 选举异常 | 部署 Anycast RP；检查 `show pim bsr-router` |
| 11 | 组播大包不通、小包正常 | 封装后超 MTU，且 DF 置位产生 MTU 黑洞 | 调整隧道 MTU 与 TCP MSS；检查 ICMP code 4 |
| 12 | PIM 邻居起不来 | 接口未开 `pim sparse-mode`，或 RPF 接口未被选为 DR | 逐接口确认 `pim` 使能与 DR 角色 |
| 13 | traceroute 停在某一跳 | 该跳不回 ICMP Time Exceeded（被 ACL 拦或限速） | 属正常现象，不代表路径断了；改看 `mtr` 丢包分布 |
| 14 | ping 显示端口不可达 | 目标存活但对应端口无监听（Type 3 code 3） | 说明网络通、服务没起 —— 是应用层问题 |
| 15 | 双栈环境下 VRRP6 不生效 | 只配了 VRRPv4，IPv6 侧未配置 VRRP6 | 分别在 IPv4/IPv6 地址族下配置并核对 VRID |

## 九、自测练习

1. 写出 VRRP 虚拟 MAC 的生成规则，并说明 VRID = 42 时的虚拟 MAC 是什么。
2. **计算题**：某 VRRP 组 Advertisement 间隔为 1 秒，备份路由器优先级为 120，求 Skew_Time 与 Master_Down_Interval。
3. **计算题**：若把 Advertisement 间隔改为 3 秒、优先级仍为 120，接管时间变成多少？这会给业务带来什么影响？
4. **计算题**：求组播地址 239.1.1.1 对应的 MAC 地址（写出低 23 位的推导过程）。
5. **计算题**：判定 224.0.1.1 与 224.128.1.1 是否映射到同一个 MAC，给出推导；并说明映射为什么恰好是 32:1。
6. **计算题**：IPv4 组播地址空间共 2^28 个组，MAC 侧可用位数是多少？据此算出每个 MAC 平均对应多少个组。
7. **排障题**：两台路由器配了相同 VRID 的 VRRP，但 `display vrrp` 显示两台都是 Master，请给出至少三条可能原因与验证方法。
8. **排障题**：某主机已成功加入组播组 239.1.1.1，但收不到源发来的数据。请给出排查顺序。
9. VRRP、HSRP、GLBP 三者在「同时转发的设备数量」上有什么区别？这带来什么业务差异？
10. 为什么 IGMP 需要 Snooping？不开启会怎样？
11. **计算题**：某台二层交换机下挂 24 个端口，其中只有 3 个端口有主机加入了组 239.1.1.1。若不开启 IGMP Snooping，该组播帧会被复制到几个端口？开启后呢？
12. 说明 PIM-SM 中 RP 的作用，以及为什么 (*,G) 共享树最终要切换成 (S,G) 最短路径树。

<details>
<summary>参考答案</summary>

1. 虚拟 MAC = `00-00-5E-00-01-{VRID}`，其中 `00-00-5E` 是 IANA 分配的 VRRP OUI，`00-01` 标识 VRRP 协议，最后一字节是 VRID。VRID = 42 = 0x2A 时，虚拟 MAC = `00:00:5E:00:01:2A`。

2. `Skew_Time = (256 − Priority) / 256 = (256 − 120) / 256 = 136 / 256 = 0.53125` 秒。`Master_Down_Interval = 3 × Advertisement_Interval + Skew_Time = 3 × 1 + 0.53125 = 3.53125` 秒 ≈ **3.53 秒**。

3. `Master_Down_Interval = 3 × 3 + 0.53125 = 9 + 0.53125 = 9.53125` 秒 ≈ **9.53 秒**。影响：主设备故障后，业务中断时间从约 3.5 秒拉长到约 9.5 秒。对 TCP 而言，超过重传超时会被感知为连接卡顿甚至中断；对语音/视频这类实时业务，9.5 秒的中断是不可接受的。因此 Advertisement 间隔通常保持默认 1 秒。

4. 239.1.1.1 = `11101111.00000001.00000001.00000001`（239 = 0xEF）。低 23 位 = 后 23 个二进制位 = `0 0000001.00000001.00000001`。拼接后 MAC = `00000001.00000000.01011110.` + 低 24 位（高位补 0）= `00000001.00000000.01011110.00000001.00000001.00000001` → **01:00:5E:01:01:01**。

5. 224.0.1.1 = `11100000.00000000.00000001.00000001`，低 23 位 = `0x000101`；224.128.1.1 = `11100000.10000000.00000001.00000001`，低 23 位同样是 `0x000101`（丢弃的第 5 位即第二字节的最高位不同）。两者 MAC 都是 `01:00:5E:00:01:01`，**映射到同一个 MAC**。恰好 32:1 的原因：组播组号 28 位，MAC 只用 23 位，丢掉 `28 − 23 = 5` 位，因此每个 MAC 对应 `2^5 = 32` 个组；且 `2^28 / 2^5 = 2^23` 恰好整除，所以是严格均匀的 32:1，没有边界例外。

6. MAC 侧可用 23 位（因为映射取的是组播 IP 的低 23 位，且 MAC 中 `01:00:5E` 之后第 4 字节最高位恒为 0）。每个 MAC 平均对应 `2^28 / 2^23 = 2^5 = 32` 个组播地址。

7. 两台都显示 Master 的原因与验证：① **认证不一致** —— 两端口令或认证类型不同，互相丢弃对方通告，`display vrrp verbose` 看认证配置；② **VRID 冲突但处于不同 VRRP 组/接口** —— 确认是否同一个三层接口、同一个 VRID；③ **虚拟 IP 配错** —— 例如两端配了不同的 VIP，实际是两组独立 VRRP，`display vrrp` 对比 VIP；④ **链路单向中断** —— 通告只去不回，两端都认为对端已死，用双向 ping 与抓包验证；⑤ **优先级都配成了 255** —— 若两端接口 IP 都等于 VIP（配置错误），会各自认为自己是 IP 拥有者。

8. 排查顺序：① 在最后一跳路由器上 `show ip mroute 239.1.1.1` 看是否有 `(S,G)` 或 `(*,G)` 表项、入接口是否正确；② `show ip rpf <源地址>` 检查 RPF 接口与实际收包接口是否一致 —— 不一致就会丢弃；③ 检查中间路由器是否都有对应表项（PIM 是否逐跳使能）；④ `show ip igmp groups` 确认接收者加组是否被路由器记录；⑤ 在源侧确认确实在发包（抓包看有没有组播流量出来）；⑥ 检查是否有 ACL 或 `ip multicast boundary` 拦掉了该组；⑦ 检查 MTU：若小包通、大包不通则是 MTU 黑洞；⑧ 检查 RP 是否可达、PIM 邻居是否正常。

9. VRRP 与 HSRP 都只有**一台设备在转发**（Master/Active），其余处于 Backup/Standby 待命，因此带宽与转发能力只用了单台的。GLBP 支持最多 **4 个 AVF 同时转发**，由 AVG 把不同主机分配到不同 AVF 的虚拟 MAC 上，实现上行流量的负载分担。业务差异：VRRP/HSRP 场景下上行带宽上限 = 单台设备上行链路带宽（例如两台设备各 1G，实际只能跑 1G）；GLBP 场景下可以跑到接近 4 台之和，同时保留冗余能力。

10. 二层交换机只会看 MAC，不知道 IP 层的组播语义。若不开启 IGMP Snooping，交换机把组播帧当作未知目的 MAC 的帧处理，按广播逻辑泛洪到同一 VLAN 内的所有端口（除入端口）。这样组播就退化成了广播，浪费带宽、增加主机 CPU 负担，还可能造成信息泄漏。开启 Snooping 后，交换机监听 IGMP Report/Leave，建立「组播 MAC → 端口」表，只向有接收者的端口转发。

11. 不开启 IGMP Snooping：组播帧会泛洪到这个 VLAN 内所有其它端口，即 `24 − 1 = 23` 个端口（入端口不回发）。开启后：只复制到那 3 个有接收者的端口 → **3 个端口**。节省了 `23 / 3 ≈ 7.7` 倍的下行复制量与带宽占用。

12. RP（Rendezvous Point）是 PIM-SM 共享树的树根。源与接收者事先都不知道对方在哪，RP 作为「约定的汇合点」让双方先接上头：接收者向 RP 发 (*,G) Join，源侧 DR 把流量用 Register 单播送到 RP，RP 再把两者对接起来，共享树 `(*,G)` 因此与源的位置无关。但共享树绕经 RP，路径往往不是源到接收者的最短路径（例如源与接收者同侧时仍要绕到 RP）。所以当接收者收到流量、得知源地址后，会计算到源的最短路径，若比经 RP 更近，就向源方向发 (S,G) Join 建立最短路径树，然后向 RP 发 Prune 退出共享树。这就是「先通后优」的设计。

</details>
