## 二、核心概念总览

排障的本质是**用最小代价把故障域切半**。下图给出「一次数据包旅程」上的检查点与对应工具：

```
  应用   ┌──────────┐   curl -v / dig   看是否有响应、响应码、DNS 是否解析
         │  PC1     │
  传输   │          │   ss -tnp         看端口是否 LISTEN、是否 ESTABLISHED
         │  主机侧   │   netstat -s      看重传率、SYN 丢弃计数
  网络   │          │   ping / mtr      看丢包与 RTT 抖动
         └────┬─────┘   ip route        看路由与默认网关
              │         arp -a          看网关 MAC 是否正常
  链路  ┌────┴─────┐   ethtool          看速率/双工/CRC 错误计数
         │  交换机   │   tcpdump -e      看 VLAN 标签、源目 MAC
         └────┬─────┘   show mac / arp  看 MAC 表、ARP 表
              │
  物理  ┌────┴─────┐   看指示灯、换网线、换端口   光功率、CRC、错包计数
         │  介质     │
         └──────────┘

  推荐顺序：先确认物理(灯/线/口) -> 再看链路(速率双工/CRC) -> 再看二层(MAC/ARP/VLAN)
            -> 再看三层(路由/掩码) -> 再看四层(端口/防火墙) -> 最后怀疑应用与对端
```

三种方法论的取舍：

| 方法论 | 起点 | 优点 | 适用场景 |
|---|---|---|---|
| 自底向上 | 物理层 | 不易漏掉底层问题 | 新上线、刚改过线缆/配置 |
| 自顶向下 | 应用层 | 快速验证「是不是应用问题」 | 单应用报错、其它应用正常 |
| 分治（对半） | 从中间（三层）切入 | 最快缩小范围 | 老网络突然故障、无明显线索 |

统一使用的教学网段：办公网 `192.0.2.0/24`、对外服务 `198.51.100.0/24`、骨干 `203.0.113.0/24`、IPv6 `2001:db8::/32`。

## 三、机制详解

### 3.1 分层排障方法论

**为什么这样设计**：网络是分层系统，每一层只对上层负责。故障必然发生在某一层，按层排查能把「可能性空间」指数级缩小。

排障的四条纪律：

1. **先确认范围**：是「一个人」还是「一群人」？是「一个应用」还是「所有应用」？范围直接决定是端侧问题还是网络侧问题。
2. **先看物理再查配置最后怀疑对端**：自己这侧 10 秒能确认的事，不要先假设对端有问题。
3. **每次只改一个变量**，改完立刻验证。同时改三处会导致「好了但不知道为什么好」。
4. **留证据**：故障现场（`tcpdump`、`show` 输出）比事后回忆可靠得多。

### 3.2 主机侧工具链

| 工具 | 解决什么问题 | 关键输出解读 |
|---|---|---|
| `ping` | 三层可达性与 RTT | `time=` 是 RTT；`Request timeout` 是丢包；`Destination host unreachable` 是本机 ARP/路由失败 |
| `traceroute` / `tracert` | 逐跳路径 | `*` 表示该跳不回 ICMP，不代表故障；末跳出现即到达 |
| `mtr` | ping + traceroute 持续统计 | 看**每一跳**的丢包率，只有「从某跳开始持续丢」才是真故障 |
| `arp -a` | 二层解析 | 网关 MAC 是否正常；同 IP 多 MAC 说明有冲突/欺骗 |
| `ip addr` / `ifconfig` | 本机接口与地址 | 地址、掩码、MTU、UP 状态 |
| `ip route` | 路由表 | 默认网关、是否有明细路由覆盖 |
| `ss -tnp` / `netstat -ntp` | 连接与监听 | `LISTEN` 才可能被连；`SYN-SENT` 堆积说明对端未应答 |
| `dig` / `nslookup` | DNS 解析 | `status:`、`ANSWER SECTION`、`Query time` |
| `iperf3` | 吞吐基准 | 测链路真实能力，排除应用瓶颈 |
| `curl -v` | HTTP 全过程 | 看 DNS → TCP 连接 → TLS → 请求 → 响应各阶段耗时 |
| `ethtool` | 网卡/链路状态 | `Speed`、`Duplex`、`Link detected`、CRC 错误计数 |

`ping` 的三个层次输出很有诊断价值：`Destination Host Unreachable`（本机到网关就失败）、`Request timeout`（发出去了没回，可能是中间丢或对端不回）、成功但 RTT 忽高忽低（链路质量或拥塞）。

### 3.3 Wireshark 显示过滤器与「跟随 TCP 流」

**显示过滤器（Display Filter）** 与 **捕获过滤器（Capture Filter）** 是两套语法：捕获过滤器用 BPF 语法（在抓之前生效、省资源），显示过滤器用 Wireshark 自有语法（在已抓到的包里筛选）。

常用显示过滤器：

```
ip.addr == 192.0.2.10                  # 源或目的任一
ip.src == 192.0.2.10 && ip.dst == 198.51.100.10
tcp.port == 443
tcp.flags.syn == 1 && tcp.flags.ack == 0     # 只过滤 SYN（找建连请求）
tcp.analysis.retransmission                  # 只看重传
http.request || http.response
dns.qry.name contains "example"
icmp.type == 3 && icmp.code == 4             # Fragmentation Needed
vlan.id == 100
```

**跟随 TCP 流（Follow TCP Stream）** 把一次会话的双向载荷按方向拼装出来，适用于看明文协议（HTTP/FTP/Telnet）和还原应用场景。右键任一 TCP 包 → Follow → TCP Stream。

### 3.4 pcap 文件格式

**解决什么问题**：抓包工具（tcpdump/Wireshark/dumpcap）都把结果存成 libpcap 格式，理解它就能写自己的解析器、也能看懂「为什么抓的包被截断了」。

**全局头（Global Header）固定 24 字节**：

| 偏移 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0 | magic_number | 4 | `0xA1B2C3D4`=微秒，`0xA1B23C4D`=纳秒；同时暗示字节序 |
| 4 | version_major | 2 | 一般为 2 |
| 6 | version_minor | 2 | 一般为 4 |
| 8 | thiszone | 4 | GMT 时区偏移，实际恒为 0 |
| 12 | sigfigs | 4 | 时间戳精度，实际恒为 0 |
| 16 | snaplen | 4 | 每包最多截取字节数（常见 65535 或 262144） |
| 20 | network | 4 | 链路类型，1 = Ethernet |

**包记录头（Packet Record Header）固定 16 字节**：`ts_sec(4) + ts_usec(4) + incl_len(4) + orig_len(4)`。其中 `incl_len` 是实际写入文件的字节数，`orig_len` 是包在线路上的原始长度；当 `incl_len < orig_len` 时说明包被 snaplen 截断（最常见的坑：抓到的包没抓住完整载荷）。

**magic 判读的一个细节**：`0xA1B2C3D4` 按大端读取正常，说明文件是大端；写成小端字节序（文件首 4 字节是 `d4 c3 b2 a1`）说明是小端。解析器必须先读 4 字节判断字节序，否则后面所有多字节字段都会读错。

### 3.5 BPF 过滤表达式

**解决什么问题**：抓包时在**内核里**就过滤掉不关心的流量，避免把磁盘写满、也避免 CPU 花在无关包上。

BPF 表达式的语法结构：

```
表达式  := 项 (('and'|'||') 项)*
项      := 因子 (('and'|'&&') 因子)*
因子    := ('not'|'!') 因子 | '(' 表达式 ')' | 原语
原语    := [src|dst] (host IP | net IP/len | port N) | tcp | udp | icmp | arp | ip
```

要点：**无方向前缀的 `host` / `port` 是「源或目的任一命中」**；加 `src` / `dst` 才限定单方向。`net 192.0.2.0/24` 中的掩码也可写成点分形式 `192.0.2.0/255.255.255.0`。

### 3.6 TTL 与 traceroute 机制

**traceroute 为什么能画出路径**：

1. 发送一个 UDP 探测包，把 IP 头的 **TTL 设为 1**。
2. 第一个路由器收到后把 TTL 减到 0，**丢弃报文并回一个 ICMP 超时报文（type 11, code 0）**，源地址就是该路由器。
3. 发送方用 TTL=2、3、4… 重复，逐跳收集回包的源地址，画出路径。
4. 当探测包到达目标，目标对高端口返回 **ICMP 端口不可达（type 3, code 3）**，标志探测结束。

**为什么会有 `*`**：中间路由器出于 ICMP 限速或安全策略不回 ICMP 超时。**`*` 不代表该跳故障**，只要后续跳还在继续、最终能到达目标，路径就是通的。

**Windows 的 tracert** 用 ICMP Echo 探测（不是 UDP），因此对不响应 ICMP 的设备会显示成 `*` 更多。

**非对称路由的坑**：traceroute 记录的是「每跳回包的源地址」。若去程走 R1→R2→R3、回程走 R3→R4→R1，则第 4 跳可能显示 R4 的地址。**不能用 traceroute 推断单向转发路径**，要验证单向路径必须两端同时抓包比对 TTL。

### 3.7 MTU / MSS 与分片

**MSS 推导公式**：

```
MSS = MTU - IP 头长度 - TCP 头长度
```

以太网 MTU=1500 时：IPv4 `MSS = 1500 - 20 - 20 = 1460`；IPv6 `MSS = 1500 - 40 - 20 = 1440`。

**IP 分片规则**：分片载荷必须是 **8 字节的整数倍**（因为片偏移字段以 8 字节为单位计数）；每片都重复一个 IP 头；MF 位在除最后一片外都为 1；最后一片 MF=0。

以 MTU=1500、IP 载荷 3000 字节为例：单片最大载荷 `floor((1500-20)/8)*8 = 1480`，于是切成 1480 + 1480 + 40 三片，偏移分别为 0 / 185 / 370（单位是 8 字节）。

**MTU 黑洞的三要素**：中间链路 MTU 更小 + 报文 DF=1 + **PMTUD 依赖的 ICMP type 3 code 4 被丢弃**。三者齐备时，大包在中间被静默丢弃，发送方反复重传，表现为「小包通、大包卡」。

## 五、关键字段 / 报文格式解剖

### 5.1 pcap 全局头（24 字节）与包记录头（16 字节）

| 字段 | 偏移 / 长度 | 作用 | 常见取值 |
|---|---|---|---|
| magic_number | 0 / 4B | 标识格式与字节序 | `0xA1B2C3D4`（微秒）、`0xA1B23C4D`（纳秒） |
| version | 4 / 4B | 版本号（主 2 字节 + 次 2 字节） | 2.4 |
| snaplen | 16 / 4B | 单包最大抓取长度 | 65535 / 262144 |
| network | 20 / 4B | 链路层类型 | 1 = Ethernet |
| ts_sec | +0 / 4B | 时间戳秒 | Unix 秒 |
| ts_usec | +4 / 4B | 时间戳微秒 | 0~999999 |
| incl_len | +8 / 4B | 实际抓取长度 | ≤ snaplen |
| orig_len | +12 / 4B | 原始包长度 | ≥ incl_len（大于即被截断） |

### 5.2 IPv4 首部关键字段（20 字节固定头）

| 字段 | 长度 | 作用 | 常见取值 |
|---|---|---|---|
| 版本 + 首部长度 | 1B | 版本（高 4 位）+ IHL（低 4 位，单位 4B） | `0x45` = IPv4 + 20B 头 |
| 总长度 | 2B | 整个 IP 分组长度（含头） | ≤ MTU |
| 标识 ID | 2B | 分片重组标识 | 每包 +1 |
| 标志 + 片偏移 | 2B | DF / MF / 13 位偏移（单位 8B） | `0x4000` = DF=1 |
| TTL | 1B | 跳数限制，每路由器减 1 | 64 / 128 / 255 |
| 协议 | 1B | 上层协议号 | 1=ICMP / 6=TCP / 17=UDP |
| 首部校验和 | 2B | 仅覆盖 IP 首部 | 每跳重算 |
| 源 / 目的地址 | 8B | 寻址 | — |

## 六、易混概念对比

| 概念 A | 概念 B | 核心区别 | 典型场景 |
|---|---|---|---|
| 捕获过滤器 | 显示过滤器 | 前者 BPF 语法、抓包前生效；后者 Wireshark 语法、抓包后筛选 | `tcpdump 'tcp port 80'` vs `tcp.port==80` |
| ping 失败 | traceroute 某跳 `*` | ping 失败是端到端不通；`*` 只是该跳不回 ICMP | `*` 不代表断，需看后续跳 |
| SYN 无响应 | SYN 收到 RST | 无响应=被丢或没到；RST=明确被拒 | 防火墙 drop vs reject |
| 丢包 | 抖动 | 丢包是包没到；抖动是 RTT 波动大 | 语音怕抖动，下载怕丢包 |
| 分片 | 分段（MSS） | 分片在 L3、由路由器做；分段由发送方按 MSS 做 | 分片应尽量避免 |
| MTU | MSS | MTU 是链路可载 IP 载荷上限；MSS 是 TCP 数据上限 | MSS = MTU - 40（IPv4） |
| 半开连接 | 连接重置 | 半开是一方消失；RST 是明确重置 | CLOSE_WAIT 堆积 vs RST 风暴 |

## 七、工程实践与最佳实践

1. **抓包前先想清楚过滤条件**，用 BPF 语法在捕获阶段就过滤。因为全量抓包会瞬间产生 GB 级文件，且高流量下丢包率上升，反而漏掉关键帧。
2. **抓包时加 `-s 0`（或足够大的 snaplen）**。因为默认 snaplen 只有 96 字节，会截断载荷，看 HTTP 正文时只能看到半截头。
3. **用 `-w file.pcap` 落盘再离线分析，避免终端刷新丢信息**。因为终端滚动缓冲有限，实时 `-X` 输出在高速流量下会丢行。
4. **关注 TCP 重传率而不是单次丢包**。因为公网上偶发丢包正常，持续重传率 >1% 才说明链路或路径有问题。
5. **mtr 要跑够时间（≥30 秒）再看丢包**。因为 ICMP 被限速时首包可能丢失，短时间统计会误判中间跳故障。
6. **排查 MTU 问题必须两端都测**。因为黑洞只影响大包，且单向可能不触发；只在一端 ping 大包会误判为「没问题」。
7. **ethtool 的 CRC / 错包计数要定期基线化**。因为增长中的 CRC 错误意味着线缆或光模块劣化，早发现能避免突发断链。
8. **先抓「正常时的包」做基线**。因为故障时的抓包需要和基线对比才能判断「这个 SYN 重传是不是异常」。
9. **防火墙两侧都要抓包**。因为只有对比「进去的包」和「出来的包」才能定位是防火墙丢了还是对端没回。
10. **不要在生产设备上长时间开 debug**。因为 debug 输出会抢占 CPU 并可能刷爆日志，排障优先用抓包与计数器。
11. **非对称路由场景用两端同时抓包 + 时间戳比对**。因为 traceroute 无法反映单向路径，只有端到端抓包才能看清去程/回程。
12. **记录每次排障的「现象-假设-验证-结论」**。因为同样的故障会复现，结构化记录能把平均恢复时间降下来。

## 八、常见陷阱清单

| # | 现象 | 根因 | 排查 / 规避 |
|---|------|------|-------------|
| 1 | tcpdump 抓到的包看不到 HTTP 正文 | 默认 snaplen 太小截断了 | 加 `-s 0` 或 `-s 262144` 抓完整帧 |
| 2 | 显示过滤器写了不生效 | 把 BPF 语法当显示过滤器用 | 显示过滤器用 `ip.addr == x`，不是 `host x` |
| 3 | traceroute 中间跳一堆 `*` 就判定故障 | `*` 只表示该跳不回 ICMP | 看 mtr 持续统计，检查最后一跳是否到达 |
| 4 | 大文件传输卡死但 ping 正常 | MTU 黑洞（DF=1 + PMTUD 的 ICMP 被丢） | 两端逐级缩小包测 MTU，中间设备 `ip tcp adjust-mss` |
| 5 | 抓包看到大量 SYN 重传、无 SYN-ACK | 服务端没监听 / 被防火墙丢 / 回程路由不通 | 在服务端 `ss -tlnp` 查监听，两端同时抓包 |
| 6 | 抓到大量 RST | 端口未监听 / 中间设备 reject / 连接被掐 | 看 RST 来自哪一端，定位是应用还是设备 |
| 7 | 连接卡在 SYN-SENT 一直不成功 | SYN 出去没有回包 | 检查路由、ACL、目标端口 |
| 8 | 抓包文件打开提示「未知文件格式」 | 字节序或 magic 判读错，或文件被截断 | 用 `file` 命令确认；确认写入完整全局头 |
| 9 | `ss` 显示大量 CLOSE_WAIT | 应用没正确 close 套接字 | 排查应用代码，不是网络问题 |
| 10 | iperf3 吞吐远低于链路带宽 | 单条 TCP 流受窗口/时延限制 | 用 `-P 4` 多流测，或算带宽时延积确认窗口够不够 |
| 11 | 只有个别协议不通，其它正常 | ACL 精确匹配了该端口/协议 | 看设备 ACL 命中计数与 deny 日志 |
| 12 | 双向都抓不到包 | 抓包点位不在转发路径上（镜像口配错） | 确认镜像源端口方向与抓包接口一致 |
| 13 | 时间戳全为 0 或负值 | pcap 纳秒/微秒 magic 判读错 | 用 magic 判断精度，纳秒值要除以 1e9 |
| 14 | 同一会话在两端看到的内容不一致 | 中间设备做了 NAT / 改写 | 两端抓包比对 IP/端口，确认是否经过 NAT |
| 15 | mtr 显示某跳丢包但业务正常 | ICMP 被限速造成的假象 | 只把「从某跳起持续丢包」当故障，单跳零星丢包忽略 |

## 九、自测练习

1. 计算：以太网 MTU=1500，IPv6 环境下 TCP 的 MSS 是多少？
2. 计算：一个 IPv4 报文 IP 头 20 字节、载荷 4000 字节，链路 MTU=1500，DF=0，将被分成几片？各片偏移是多少？
3. 计算：pcap 全局头 24 字节 + 3 条包记录，其中帧长分别为 60 / 100 / 74 字节，求整个 pcap 文件的总字节数。
4. 写出 Wireshark 显示过滤器，只显示 `192.0.2.10` 与 `198.51.100.10` 之间的 TCP 443 报文。
5. 排障：某主机能 ping 通网关，但打不开网页，`curl -v` 卡在 `Trying 198.51.100.10...`，如何定位？
6. 排障：交换抓包发现大量客户端发 SYN、服务端无任何回包，可能原因有哪些？
7. 解释 traceroute 中间显示 `* * *` 是否一定代表该跳故障。
8. 计算：若 TCP 窗口 65535 字节，RTT 40ms，单条流的理论最大吞吐是多少？说明为什么实测常常更低。
9. 说明捕获过滤器与显示过滤器的语法差异，并各举一例。
10. 给出 MTU 黑洞的三个必要条件，并写出两种缓解手段。

<details>
<summary>参考答案</summary>

**1.** 代入 MSS 公式：

```
MSS = MTU - IPv6 首部 - TCP 首部
    = 1500 - 40 - 20
    = 1440 字节
```

**2.** 分片计算。

- 单片最大载荷：`floor((1500 - 20) / 8) * 8 = floor(1480 / 8) * 8 = 185 * 8 = 1480` 字节。
- 4000 字节载荷：`4000 = 1480 + 1480 + 1040`，即 **3 片**。
- 片偏移（单位 8 字节）：
  - 第 1 片偏移 `0 / 8 = 0`；
  - 第 2 片偏移 `1480 / 8 = 185`；
  - 第 3 片偏移 `2960 / 8 = 370`。
- 验证：`370 × 8 + 1040 = 2960 + 1040 = 4000` ✓。

**3.** 文件总字节数。

```
全局头 = 24 字节
每条包记录 = 16(记录头) + 帧长
总长 = 24 + (16 + 60) + (16 + 100) + (16 + 74)
     = 24 + 76 + 116 + 90
     = 306 字节
```

**4.** 显示过滤器：

```
ip.addr == 192.0.2.10 && ip.addr == 198.51.100.10 && tcp.port == 443
```

注意：两个 `ip.addr` 同时出现时 Wireshark 要求报文同时满足「涉及 A」与「涉及 B」，即只保留两端之间的报文（避免出现 A 与第三方、B 与第三方的报文）。

**5.** 定位步骤。

1. `curl -v` 卡在 `Trying IP...` 表示 TCP 连接阶段无响应，问题在 L3/L4。
2. `ping 198.51.100.10` 测三层：通 → 问题在端口/防火墙；不通 → 问题在路由。
3. `ip route get 198.51.100.10` 确认走哪条路由、出接口与源地址。
4. 在主机 `sudo tcpdump -nn -i any host 198.51.100.10` 看 SYN 是否发出、有无 SYN-ACK。
5. 无 SYN-ACK → 在中间防火墙 / 目标端再抓，确认是被丢还是对端没监听（对端 `ss -tlnp | grep 443`）。

**6.** 可能原因（按概率排序）。

1. **路径不可达**：客户端到服务端的三层路由缺失或指向黑洞，SYN 被中间设备丢弃。
2. **防火墙拦截**：中间 ACL / 安全组 drop 了 443（且未回 RST）。
3. **服务端未监听**：端口没开，若默认策略是 drop 则表现为无响应（若回 RST 则表现为立即拒绝）。
4. **回程路由不通**：SYN 到了，但 SYN-ACK 的回程被丢（非对称路由常见）。
5. **服务端半连接队列满**：被 SYN Flood 或连接数打满，新 SYN 被丢。

**7.** 不一定。

`*` 只说明该跳没有回 ICMP 超时报文，原因可能是：该跳设备对 ICMP 做了限速、策略禁止回 ICMP、或者该跳转发快但回 ICMP 时被丢。**判据是「后续跳是否继续响应」**：若第 3 跳是 `*`、第 4 跳正常响应并最终到达目标，说明路径是通的，第 3 跳的 `*` 只是它不回 ICMP。

**8.** 理论吞吐（带宽时延积）：

```
BDP = 窗口 / RTT = 65535 字节 / 0.040 s
    = 1638375 字节/s
    ≈ 1.638 MB/s × 8
    ≈ 13.1 Mbit/s
```

实测更低的原因：① 窗口未必能一直开满（受接收端缓存、拥塞控制影响）；② 存在丢包触发的拥塞退避；③ 应用层开销与磁盘 IO；④ 首字节之后的 ACK 处理延迟。要提升需增大窗口（窗口扩大选项）或减少 RTT。

**9.** 语法差异。

- **捕获过滤器**：libpcap/BPF 语法，作用于抓包前。例：`tcpdump -i en0 'tcp port 443 and host 192.0.2.10'`。
- **显示过滤器**：Wireshark 自有语法，作用于已抓到的包。例：`tcp.port == 443 && ip.addr == 192.0.2.10`。
- 关键区别：捕获过滤器用 `host/port/and/or/not`，显示过滤器用 `ip.addr==/tcp.port==/&&/||/!` 且可访问协议字段（如 `tcp.flags.syn`）。

**10.** 三个必要条件与缓解。

- **必要条件**：
  1. 路径上存在 MTU 更小的链路（如 1400）。
  2. 发送的报文设置了 **DF=1**，中间设备不能分片。
  3. **PMTUD 依赖的 ICMP type 3 code 4 被丢弃**，发送方收不到「请下调 MTU」的通知。
- **缓解手段**：
  1. 在路由器上对 TCP 会话改写 MSS：`ip tcp adjust-mss 1360`（Cisco）/ `tcp adjust-mss 1360`（华为）。
  2. 在主机上开启黑洞探测：`sysctl net.ipv4.tcp_mtu_probing=1`，内核会自动二分试探并下调 MTU。

</details>
