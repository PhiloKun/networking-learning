## 二、核心概念总览

云网络的本质是**在物理网络之上再叠一张「软」网络**。下图把本章骨架铺开：

```
  ┌────────────────────────────── 云上资源视图（租户看到的）──────────────────────────────┐
  │  VPC (10.0.0.0/16)   子网A(10.0.1.0/24)  子网B(10.0.2.0/24)  安全组 / 网络ACL          │
  │  路由表 / NAT网关 / 弹性IP / 对等连接 / 云企业网 / 专线                                │
  └──────────────────────────────────────────┬───────────────────────────────────────────┘
                                             │  依赖
  ┌──────────────────────────────────────────▼───────────────────────────────────────────┐
  │  K8s / 容器网络：CNI 插件    Pod 网络模型「每个 Pod 一个 IP」                          │
  │  ClusterIP / NodePort / Ingress / kube-proxy(iptables|IPVS) / NetworkPolicy           │
  └──────────────────────────────────────────┬───────────────────────────────────────────┘
                                             │  依赖
  ┌──────────────────────────────────────────▼───────────────────────────────────────────┐
  │  Linux 网络虚拟化：netns / veth pair / bridge / tun-tap / iptables / nftables        │
  └──────────────────────────────────────────┬───────────────────────────────────────────┘
                                             │  依赖
  ┌──────────────────────────────────────────▼───────────────────────────────────────────┐
  │  Overlay 隧道：VXLAN(50B) / GENEVE(50B) / GRE(38B) / NVGRE(42B)  + EVPN 控制面        │
  └──────────────────────────────────────────┬───────────────────────────────────────────┘
                                             │  依赖
  ┌──────────────────────────────────────────▼───────────────────────────────────────────┐
  │  Underlay 物理网络：三层 IP 可达（OSPF/IS-IS/BGP），只需提供 VTEP 之间的可达性        │
  └──────────────────────────────────────────────────────────────────────────────────────┘
```

各层职责一句话：**Underlay 只管 IP 可达，Overlay 提供二层/分段，Linux 虚拟化提供本机管道，CNI 把管道接成集群网络，云组件把这一切做成可编排的资源。**

为什么非要用 Overlay：

| 物理网络方案的局限 | 具体数字 | Overlay 的解法 |
|---|---|---|
| VLAN 数量不够 | 12 位 VID，最多 4094 个 | VXLAN 24 位 VNI，16,777,215 个段 |
| 二层不能跨三层扩展 | STP 收敛慢、广播域大 | 用 UDP 隧道跨三层承载二层帧 |
| 物理交换机 MAC 表压力大 | 大二层需要海量 MAC 表项 | 只有 VTEP 参与 underlay 转发 |
| 新租户开通慢 | 需逐台设备改 VLAN 配置 | 控制器集中下发，分钟级开通 |

统一使用的教学网段：办公网 `192.0.2.0/24`、对外服务 `198.51.100.0/24`、骨干/VTEP `203.0.113.0/24`、Pod CIDR `10.244.0.0/16`。

## 三、机制详解

### 3.1 为什么需要 Overlay

**解决什么问题**：数据中心需要给成千上万个租户/业务提供互相隔离的二层网络，而物理网络受 VLAN 4094 上限、STP 收敛慢、跨机房无法二层延伸的限制。

**Overlay 的思路**：把内层的以太网帧整体当作载荷，封装进一个跨三层可达的隧道里传输。内层网络的拓扑与物理拓扑解耦，物理网络退化为「只要 VTEP 之间 IP 可达」。这就是 **MAC-in-UDP** 的由来。

关键角色 **VTEP（VXLAN Tunnel End Point）**：封装与解封装的端点，通常是物理交换机、服务器上的虚拟交换机（OVS）或 DPU。VTEP 有一个 underlay IP，负责把内层帧「塞进」UDP 隧道。

### 3.2 隧道技术对比

| 隧道 | 封装 | 标识字段 | 固定开销 | 特点 |
|---|---|---|---|---|
| VXLAN | MAC-in-UDP | 24 位 VNI | 50 B | 事实标准，生态最全，目的端口 4789 |
| GENEVE | 以太网-in-UDP | 24 位 VNI + TLV 选项 | 50 B+ | 头部可扩展，便于加元数据 |
| NVGRE | MAC-in-GRE | 24 位 TNI（藏在 GRE Key） | 42 B | 微软系推动，生态较弱 |
| GRE | IP-in-GRE | 无段标识 | 38 B | 简单，但不隔离，靠 VRF 区分 |
| IPsec | ESP | SPI | 50~73 B | 加密，常与 VXLAN 叠加做跨站点加密 |

**开销口径统一**：外层以太网 14 B + 外层 IPv4 头 20 B + 隧道自身头部。VXLAN = 14 + 20 + 8(UDP) + 8(VXLAN) = 50 B。

**VXLAN 头 8 字节布局**：

```
 字节:   0        1    2    3     4    5    6     7
      +--------+----+----+----+--------+--------+--------+--------+
      | Flags  |   Reserved    |        VNI (24 位)     | Reser. |
      +--------+----+----+----+--------+--------+--------+--------+
        0x08     0    0    0    <-- VNI 的高中低三字节 -->   0
        (I 位)
```

I 位（0x08）置 1 表示「VNI 字段有效」；VNI 占第 4~6 字节共 24 位。

### 3.3 EVPN：用控制面学习取代泛洪

**解决什么问题**：早期 VXLAN 用「泛洪 + 学习」建立转发表（数据面学习），在大规模数据中心会导致未知单播泛洪风暴。**EVPN（Ethernet VPN，RFC 7432）** 用 BGP 作为控制面，让 VTEP 之间**提前交换 MAC/IP 可达信息**，把泛洪变成查表。

BGP EVPN 的常用路由类型：

| 类型 | 名称 | 携带内容 | 解决什么 |
|---|---|---|---|
| Type 2 | MAC/IP Advertisement | 内层 MAC、内层 IP、VNI、下一跳 VTEP | 主机 MAC/IP 可达性，取代数据面学习 |
| Type 3 | Inclusive Multicast Ethernet Tag | VTEP IP、VNI、隧道类型 | 构建「每 VNI 一棵」的泛洪/组播树，用于 BUM 流量 |
| Type 5 | IP Prefix Route | IP 前缀、下一跳 | 三层互联（L3VPN over VXLAN），打通跨子网 |

**Type 2 的工作方式**：主机上线后，本端 VTEP 通过控制面（或 ARP 代答）学到 `MAC ↔ IP ↔ 端口`，然后用 BGP EVPN 通告给其它 VTEP。远端 VTEP 收到后写入转发表，后续转发直接命中，不再泛洪。

### 3.4 Overlay 的 MTU 与开销规划

**核心约束**：物理 MTU = 1500，封装开销 50 B（VXLAN），则内层可用 IP MTU = 1450，内层 TCP MSS = 1450 - 20 - 20 = 1410。

**不规划的三个后果**：

1. **MTU 黑洞**：内层主机按 1500 发，封装后 1550 > 1500，DF=1 时被丢且 PMTUD 的 ICMP 常被拦，大包卡死。
2. **外层分片**：DF=0 时外层分片，重组开销大、丢一片整包作废，吞吐与抖动恶化。
3. **应用超时**：表现为「ping 通、SSH 能登、传大文件或大页面卡死」，非常容易被误判为应用故障。

**三种规划方案**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A 调小内层 MTU | 内层主机与虚机镜像统一设 MTU 1450 / MSS 1410 | 需逐台改，存量镜像难统一 |
| B MSS 钳制 | 虚拟网关执行 `ip tcp adjust-mss 1410` | 只覆盖 TCP，UDP/ICMP 不受益 |
| C Underlay 巨帧 | 物理与隧道链路 MTU 设 9000 | 要求全路径一致，任一跳没改就断 |

工程上最常用的是 **B + 部分 C 的组合**：隧道链路启用巨帧，同时保留 MSS 钳制兜底。

### 3.5 NFV 与 VNF/CNF

**NFV（Network Function Virtualization）** 把防火墙、负载均衡、路由器等**网元功能软件化**，跑在通用服务器上。

- **VNF（Virtual Network Function）**：以虚拟机形式部署的网元功能。
- **CNF（Cloud-native Network Function）**：以容器形式部署、符合云原生规范（声明式、可编排、可弹性伸缩）。
- **MANO**：NFV 的管理与编排框架（NFVO + VNFM + VIM）。

对比：传统网元是专用硬件（如专用防火墙设备），NFV 是「x86 服务器 + 软件」，优势是弹性与成本，代价是转发性能（需 DPDK/SR-IOV/DPU 加速）。

### 3.6 Linux 网络虚拟化

| 组件 | 作用 | 典型用法 |
|---|---|---|
| netns（network namespace） | 网络栈隔离，每个 ns 独立接口/路由/iptables | `ip netns add red`，模拟多台主机 |
| veth pair | 一对虚拟网卡，一端进 ns 一端留主机 | 连接 netns 与 bridge |
| bridge | 软件二层交换机 | `ip link add br0 type bridge`，把 veth 接入 |
| tun / tap | 用户态程序读写三层/二层流量的接口 | VPN、虚拟机网卡（tap） |
| iptables / nftables | 包过滤与 NAT | `iptables -t nat -A POSTROUTING ...` |
| VRF | 路由表隔离 | 多租户路由表隔离 |

**一个最小实验拓扑**：

```
  +----------------+                    +----------------+
  | netns red      |  veth-red  <---->  |  br0 (bridge)  |  <----> eth0 (主机物理网卡)
  | 10.244.1.2/24  |  veth-red-br       |  10.244.1.1/24 |
  +----------------+                    +----------------+
```

这就是容器网络（CNI）的底层实现方式：每建一个 Pod，就创建一对 veth，一端放进 Pod 的 netns，另一端接入主机 bridge（或直接进路由表）。

### 3.7 容器与 K8s 网络

**CNI（Container Network Interface）** 是容器运行时与网络插件的标准接口。CNI 插件负责：创建 veth、分配 IP、配置路由、设置策略。

**Pod 网络模型的三条规则**：

1. 每个 Pod 有**唯一 IP**（集群内不 NAT 即可互访）。
2. 同一 Pod 内所有容器**共享同一个 netns 与 IP**（通过 pause 容器持有）。
3. Pod 之间通信**不需要 NAT**（无论是否跨节点）。

**两类 CNI**：

- **Overlay 型**（Flannel VXLAN、Calico IPIP/VXLAN）：跨节点用隧道封装，对 underlay 无要求，但有封装开销。
- **路由型**（Calico BGP）：把 Pod CIDR 通过 BGP 通告给物理网络，节点间直接路由，无封装开销、性能好，但要求物理网络能承载 Pod 路由（或使用 RR）。

**Service 与 kube-proxy**：ClusterIP 是虚拟 IP，靠每台节点上的 kube-proxy 写规则实现。

- **iptables 模式**：规则数 ≈ `服务数 + 端点数`，每包**线性匹配**；任何 Service/Endpoint 变更都要重写整条链。数千 Service 时连接建立时延与 CPU 明显上升。
- **IPVS 模式**：内核哈希表，匹配 O(1)，只增删受影响条目，适合大规模集群。
- **eBPF（Cilium）**：把转发逻辑做成 eBPF 程序，无规则链、可观测性更好。

### 3.8 云上网络组件

| 组件 | 职责 | 关键点 |
|---|---|---|
| VPC | 租户专属的虚拟网络 | 需指定 CIDR（如 10.0.0.0/16），跨 VPC 默认隔离 |
| 子网 | VPC 内的地址段 | 通常绑定一个可用区，分公有/私有子网 |
| 路由表 | 决定子网内流量去向 | 每个子网关联一张路由表 |
| 安全组 | 实例级**有状态**虚拟防火墙 | 只支持允许规则，回包自动放行 |
| 网络 ACL | 子网级**无状态**访问控制 | 支持允许+拒绝，回包要显式放行 |
| NAT 网关 | 让私有子网出公网 | 只做 SNAT，外部不能主动访问内网 |
| 弹性 IP（EIP） | 可绑定的公网 IP | 可动态绑定/解绑实例 |
| 对等连接 | 两个 VPC 私网互通 | 地址段不能重叠 |
| 云企业网 / 专线 | 多 VPC 与本地数据中心互联 | 星型拓扑集中路由 |

**安全组 vs 网络 ACL 的核心区别**：安全组是**有状态**的（出向请求的回包自动允许）、作用在**实例**上、只有 allow 规则；网络 ACL 是**无状态**的（回包必须显式允许）、作用在**子网**上、支持 allow + deny。两个方向都要显式放行是网络 ACL 最常见的坑。

运行：

```

```

## 五、关键字段 / 报文格式解剖

### 5.1 VXLAN 头（8 字节）

| 字段 | 长度 | 作用 | 常见取值 |
|---|---|---|---|
| Flags | 1 字节 | 标志位，I 位表示 VNI 有效 | `0x08` |
| Reserved | 3 字节 | 保留，发送置 0 | `0x000000` |
| VNI | 3 字节（24 位） | 租户/网段标识 | 0 ~ 16,777,215 |
| Reserved | 1 字节 | 保留，发送置 0 | `0x00` |

### 5.2 VXLAN 外层封装各字段

| 层 | 字段 | 长度 | 取值 |
|---|---|---|---|
| 外层以太网 | 目的/源 MAC、类型 | 14 B | 类型 `0x0800` |
| 外层 IPv4 | 协议 | 1 B | `17`（UDP） |
| 外层 IPv4 | 源/目的 IP | 8 B | 两端 VTEP 地址 |
| 外层 UDP | 目的端口 | 2 B | `4789` |
| 外层 UDP | 源端口 | 2 B | 按内层五元组哈希生成（用于 ECMP 负载分担） |
| VXLAN | VNI | 3 B | 与内层网段一一对应 |

> 外层 UDP 源端口由内层流哈希生成，这是让 underlay 的 ECMP 能把不同内层流分散到不同物理链路的常用手法。

### 5.3 云网络组件字段对照

| 组件 | 状态性 | 作用范围 | 规则类型 |
|---|---|---|---|
| 安全组 | 有状态 | 实例 / ENI | 仅 allow |
| 网络 ACL | 无状态 | 子网 | allow + deny |
| NAT 网关 | 有状态（连接跟踪） | 私有子网出口 | 仅 SNAT |
| 对等连接 | — | VPC 之间 | 需两侧路由表配置 |

## 六、易混概念对比

| 概念 A | 概念 B | 核心区别 | 典型场景 |
|---|---|---|---|
| Overlay | Underlay | 前者是叠加的虚拟网络，后者是承载它的物理 IP 网络 | VXLAN vs 物理 Spine-Leaf |
| VXLAN | VLAN | VXLAN 24 位 1600 万段且跨三层；VLAN 12 位 4094 段且需二层直达 | 云数据中心 vs 传统园区 |
| 数据面学习 | 控制面学习（EVPN） | 前者泛洪学习、有风暴；后者 BGP 提前通告、查表转发 | 老方案 vs 现代 DC |
| 安全组 | 网络 ACL | 有状态实例级 vs 无状态子网级 | 云主机防护 vs 子网边界 |
| VNF | CNF | 前者虚拟机上跑网元，后者容器化、云原生 | 传统 NFV vs 5G 云原生网元 |
| ClusterIP | NodePort | 前者仅集群内可达；后者在每个节点开端口对外 | 服务间调用 vs 对外暴露 |
| iptables 模式 | IPVS 模式 | 线性匹配规则链 vs 哈希表 O(1) | 小集群 vs 大规模集群 |
| Overlay CNI | 路由型 CNI | 有封装开销 vs 无封装但需物理网络承载 Pod 路由 | Flannel VXLAN vs Calico BGP |

## 七、工程实践与最佳实践

1. **Overlay 上线前先规划 MTU**。因为 VXLAN 固定吃 50 B，内层必须降到 1450/MSS 1410，否则必然踩 MTU 黑洞。
2. **Underlay 隧道链路启用巨帧（9000）**。因为这样内层可继续用标准 1500，减少对内层主机的侵入，也是业界主流做法。
3. **MSS 钳制作为兜底始终保留**。因为 UDP 与 ICMP 不受 MSS 影响，且存量虚机的 MTU 未必统一。
4. **VTEP 用 Loopback 地址且保证 underlay 可达**。因为隧道源地址若随物理口抖动，隧道会闪断——用 Loopback 提供稳定性。
5. **优先用 EVPN 而非泛洪学习**。因为泛洪在大规模下会形成 BUM 风暴，EVPN 把转发表提前通过 BGP 收敛好。
6. **VXLAN 外层 UDP 源端口按内层流哈希**。因为这样 underlay 的 ECMP 才能把不同内层流分散到多条物理链路，避免单链路拥塞。
7. **CNI 选择要匹配规模与技能栈**。因为 Overlay CNI 对物理网络无要求但有效能开销，路由型 CNI 性能好但要物理网络能承载 Pod 路由。
8. **监控 Pod CIDR 水位而非只看总量**。因为地址耗尽常常是某个节点池先用尽，总量看还有富余。
9. **建立孤儿地址回收机制**。因为容器异常退出不走正常删除流程时，IP 会永久泄漏（本例 20% 泄漏即累积 364 个）。
10. **大规模集群用 IPVS 或 eBPF 替代 iptables**。因为 iptables 每包线性匹配，数千 Service 时连接建立时延会明显上升。
11. **安全组与网络 ACL 双向都要确认**。因为网络 ACL 是无状态的，回程必须显式放行，漏了会出现「请求进去了但回不来」。
12. **跨 VPC 互联前先校验地址段不重叠**。因为对等连接无法处理重叠网段，一旦重叠只能重新规划或做 NAT。

## 八、常见陷阱清单

| # | 现象 | 根因 | 排查 / 规避 |
|---|------|------|-------------|
| 1 | 隧道建好、ping 通、传大文件卡死 | Overlay MTU 未规划，MTU 黑洞 | 内层 MTU 1450 / MSS 1410，或 underlay 巨帧 |
| 2 | 虚机迁到新宿主机后网络不通 | 新节点未加入同一 VNI / VTEP 未通告 | 核对 VNI 一致性与 EVPN Type 3 泛洪树 |
| 3 | 大规模下未知单播泛洪风暴 | 用数据面学习而非 EVPN | 部署 EVPN，或限制泛洪域 |
| 4 | 跨子网 Pod 不通但同子网正常 | 缺少 Type 5 前缀路由 / L3 网关未配 | 补 BGP EVPN Type 5，检查集中式网关 |
| 5 | 安全组放通了却仍不通 | 网络 ACL 是无状态，回程未放行 | 网络 ACL 入向与出向双向放行临时端口 |
| 6 | 对等连接建立后互访不通 | 路由表未加对端网段 | 两侧路由表都要加指向对等连接的路由 |
| 7 | 多个 Service 时新建连接变慢 | iptables 线性匹配规则链 | 切 IPVS/eBPF，或减少 Service 数 |
| 8 | Service 后端看不到真实客户端 IP | externalTrafficPolicy=Cluster 触发 SNAT | 改 Local 或走 LB 透传 |
| 9 | 某节点 Pod 无法创建，报地址不足 | 该节点 Pod CIDR 已耗尽（回收延迟/泄漏） | 监控单节点池水位，修复回收逻辑 |
| 10 | 容器重建后 IP 变了，配置失效 | 用 Pod IP 直接依赖 | 用 Service/DNS 而非 Pod IP |
| 11 | VXLAN 流量在 underlay 走单链路拥塞 | 外层 UDP 源端口固定，ECMP 无法分散 | 按内层流哈希源端口 |
| 12 | 加密后吞吐骤降 | IPsec 叠加 VXLAN 开销大且 CPU 加密瓶颈 | 用支持加解密卸载的网卡/DPU，或评估必要性 |
| 13 | VRF 隔离的两租户互相能通 | 接口未绑定 VRF 或路由泄漏 | 检查接口 VRF 归属与路由引入策略 |
| 14 | 新建 Pod 跨节点访问延迟高 | CNI 走隧道且路径未优化 | 用路由型 CNI 或优化 underlay 路径 |
| 15 | 云上实例能出公网但外部 ping 不进 | NAT 网关只做 SNAT | 这是设计如此，需对外则绑 EIP 或做端口映射 |
| 16 | 集群节点时间不同步导致证书/TLS 失败 | 依赖时钟的组件未同步 | 所有节点启用 NTP，偏差控制在秒级内 |

## 九、自测练习

1. 计算：VXLAN 在物理 MTU 1500 下，内层可用 IP MTU 与 IPv4 TCP MSS 分别是多少？
2. 计算：一个内层 1400 字节的 IP 报文经 VXLAN 封装后，外层 IP 报文长度是多少？会超过 1500 吗？
3. 计算：GRE 隧道（外层 IP 20 + GRE 基本头 4）在物理 MTU 1500 下内层 MTU 与 MSS 是多少？
4. 计算：VXLAN 的 VNI 共能表示多少个二层段？与 VLAN 的 4094 相差多少倍？
5. 写出 VXLAN 头的 8 字节布局，并说明 VNI=4096 时头 8 字节的十六进制是什么。
6. 排障：K8s 集群里同节点 Pod 互通、跨节点 Pod 不通，列出三种可能原因与验证方法。
7. 排障：某应用在物理机上正常，迁到 K8s 后大文件上传偶发卡死，如何定位？
8. 说明安全组与网络 ACL 的三点核心区别，并解释为什么「回程」是网络 ACL 最容易漏的地方。
9. 解释为什么 EVPN 能消除未知单播泛洪，Type 3 路由在其中起什么作用。
10. 计算：5000 个 Service、每个 3 个 Endpoint，iptables 模式在 KUBE-SERVICES 链上的最坏匹配次数是多少？若每条约 0.3 µs，最坏增加多少时延？

<details>
<summary>参考答案</summary>

**1.** VXLAN 内层 MTU 与 MSS。

- VXLAN 固定开销 = 外层以太网 14 + 外层 IP 20 + UDP 8 + VXLAN 8 = **50 B**
- 内层可用 IP MTU = `1500 - 50 = 1450 B`
- IPv4 TCP MSS = `1450 - 20(内层 IP) - 20(TCP) = 1410 B`

**2.** 内层 1400 字节报文的封装长度。

- 外层 IP 报文长度 = 内层报文 1400 + VXLAN 固定开销中的「外层 IP 20 + UDP 8 + VXLAN 8」= `1400 + 36 = 1436 B`
- 注意口径：外层以太网 14 B 不在「IP 报文」长度内，它属于链路层。
- `1436 ≤ 1500`，**不会超过**。真正会超的是内层取满 1500 时：`1500 + 36 = 1536 > 1500`。

**3.** GRE 隧道内层 MTU 与 MSS。

- 开销 = 外层 IP 20 + GRE 基本头 4 = 24 B（若计入外层以太网则为 38 B）
- 内层可用 IP MTU = `1500 - 24 = 1476 B`
- 内层 IPv4 TCP MSS = `1476 - 20 - 20 = 1436 B`

**4.** VNI 容量对比。

- VNI 24 位：共 `2^24 = 16,777,216` 个取值，其中 0 与 16,777,215 通常保留，可用约 **16,777,215** 个（常说 1600 万个）
- VLAN VID 12 位可用 4094 个
- 倍数 = `16,777,215 / 4094 ≈ 4097.7` 倍，约 **4100 倍**。

**5.** VXLAN 头布局与 VNI=4096 的编码。

- 布局：`Flags(1) | Reserved(3) | VNI(3) | Reserved(1)`
- VNI = 4096 = `0x001000`
- 编码值 = `(0x08 << 56) | (0x001000 << 8) = 0x0800000000100000`
- 8 字节十六进制：`08 00 00 00 00 10 00 00`

**6.** 跨节点 Pod 不通的原因与验证。

1. **underlay VTEP 之间不可达**：查两节点 VTEP 地址互相 `ping`，看 underlay 路由/防火墙。
2. **VNI 或隧道配置不一致**：在两端 `ip -d link show vxlan0` 对比 VNI、远端 IP、目的端口。
3. **节点间 UDP 4789 被禁**：`tcpdump -i any udp port 4789` 看封装包是否到达对端。
4. 补充可能：CNI 路由未写入、iptables 策略丢包（`iptables -t nat -L`、`nft list ruleset`）。

**7.** 大文件上传偶发卡死的定位。

1. 典型 MTU 黑洞：小请求正常、大包卡死。
2. 在 Pod 内 `ping -M do -s 1472 <对端>` 逐级缩小，找到断裂的包长（若 1400 左右断裂即坐实）。
3. 检查隧道叠加情况：VXLAN 内层 MTU 应为 1450、MSS 1410；IPsec 叠加后更低（本例约 1390/1350）。
4. 处理：在 CNI/网关上设置 MSS 钳制，或 underlay 启用巨帧；确认 PMTUD 的 ICMP 未被拦截。

**8.** 安全组与网络 ACL 的三点区别与回程问题。

- 区别：
  1. **状态性**：安全组有状态（回包自动放行）；网络 ACL 无状态（回包需显式规则）。
  2. **作用范围**：安全组作用在实例/ENI；网络 ACL 作用在子网。
  3. **规则类型**：安全组只有 allow；网络 ACL 支持 allow + deny。
- 回程易漏的原因：客户端与服务器通信时，服务器的**响应**在「网络 ACL 出向」方向，而客户端侧还有「网络 ACL 入向」的临时端口。由于无状态，这些回包不会被自动放行，必须显式放开临时端口段（如 1024-65535）。实践中常见错误是只放行了请求方向。

**9.** EVPN 消除泛洪的原理与 Type 3 的作用。

- EVPN 用 BGP 作为控制面，VTEP 之间**提前通告** `MAC ↔ IP ↔ VTEP` 的映射（Type 2）。这样远端 VTEP 在转发前就已有转发表项，不需要「收到未知单播就泛洪」。
- **Type 3（Inclusive Multicast Ethernet Tag Route）** 的作用是：为每个 VNI 构建一棵**泛洪/组播树**（Inclusive Multicast Tree），让 VTEP 知道「同一个 VNI 里还有哪些远端 VTEP」。它解决的是 BUM 流量（广播、未知单播、组播）的**分发范围**问题——确保泛洪只发给该 VNI 的成员，且无需数据面学习。
- 两者配合：Type 3 定义「泛洪给谁」，Type 2 提供「已知单播查表转发」，从而把未知单播降到最低。

**10.** iptables 最坏匹配次数与时延。

- KUBE-SERVICES 链上每个 Service 一条 jump 规则，最坏情况要扫遍所有 Service 才命中：
  - 匹配次数 = `5000` 条
- 时延：`5000 × 0.3 µs = 1500 µs = 1.5 ms`
- 说明：这是**连接建立**时的额外时延（命中后由 conntrack 记录，后续包不再扫）；端点数 15000 只影响 KUBE-SEP 链上某个服务的分发匹配，不叠加到全局链。IPVS 用哈希查找把这 1.5 ms 降到微秒级。

</details>
